# T-0055: Loop 角色能力、质量测试体系与 v3.11.2 缺陷治理修复

## Status

`completed`

## Phase

S6-delivery

## Objective

在不扩张到真实业务项目、不修改 AGENTS.md、不替代用户 gate 决策的前提下，系统提升 11 个 Loop 角色的能力密度与可验证性，统一质量/测试执行语义，并分阶段修复 v3.11.2 已确认的治理缺陷。

## Design Constraint

角色设计必须“超高质量但不臃肿”：使用统一 canonical schema；每个角色只补充差异化内容，不重复通用规则。每角色最多 2–3 个高信息量 challenge，所有规则必须对应检查、失败语义、升级或证据字段。

## Scope

1. 基线审计与范围冻结（只读）
2. 11 角色精简高密度能力设计
3. 角色 CONTRACT/SKILL/profile/challenge/certification 一致性修复
4. 质量与测试基础设施修复
5. v3.11.2 P1/P2 缺陷分批修复
6. 全角色挑战、独立复核、缺陷汇总与重新认证
7. 修复后回归与用户 closeout

## Role Template (canonical, 12 fields)

Mission; Authority; Inputs; Outputs; Core Checks; Failure Semantics; Tools; Challenges; Veto/Escalation; Handoff; Freshness; Known Blind Spots。

通用状态、finding、evidence、认证生命周期只定义一次，角色文件不得复制整套规则。

## Role Priorities

- main-thread：编排和结构化汇总，不专业裁决，不替代用户批准。
- product-manager：需求歧义、验收反例、不可验证目标。
- project-manager：依赖、范围漂移、task/gate/evidence 一致性。
- system-architect：跨层一致性、失败模式、可观测性、降级边界。
- module-architect：契约、状态/错误语义、版本兼容、并发；空集合不等于成功。
- developer：异常路径、原子性、资源生命周期、兼容性、回归。
- quality-engineer：真实退出码、stdout/stderr、0/0、skip/unavailable、coverage scope、版本/seeded defects/回归。
- test-engineer：负面路径、未知枚举、跨层、TOCTOU、缓存失效、冲突矩阵、测试有效性。
- security-engineer：fail-open、权限、敏感信息、依赖、工具调用、证据篡改和扫描范围。
- independent-reviewer：保持不可写独立性，增加证据真实性、关键命令复核、范围覆盖证明和 NOT_VERIFIED。
- delivery-manager / release-engineer：交付完整性、版本/evidence/残余风险与制品/回滚边界；构建成功不等于用户接受或生产批准。

## Expanded Root-Cause Scope

The baseline and subsequent repair stages must also verify and, where confirmed, remediate:

- takeover is not an atomic operation across plugin/runtime/state/continuity layers;
- onboarding may overwrite or reset an existing project state instead of using discover → validate → migration plan → approval → atomic migration → projection verification;
- state, task graph, gate register, task file, and HANDOFF lack a single authoritative source and transactional projection;
- continuity/HANDOFF hash dependencies may form a self-reference cycle;
- close-session behavior may mix rendering, validation, repair, and checkpoint mutation instead of being an idempotent renderer;
- there is no explicit, machine-verifiable end-to-end takeover lifecycle state;
- version, schema, and historical contract compatibility may drift without migration validation;
- null-task, checkpoint acknowledgement, and governance-metadata versus handoff-content boundaries may have unsafe paths;
- historical manual edits and multi-version tool use may amplify design defects into state drift.
