# T-0106: Better Harness 融合与 LE 去臃肿升级 — 总设计 + 全仓库漏洞排查（candidate-only）

## 任务概述

对 QoderAI/better-harness（BH）完成逐行深度调研（4 路 subagent + 主干阅读，覆盖 scripts/、
skills/、references/、models/、templates/、docs/specs/、test/ 全部 549 文件），产出 BH 与
loop-engine（LE）逐项优劣对比。本任务把调研结论转化为可执行的升级路径：

1. **设计漏洞全仓库排查**（用户关切：context_packager 按字符截断/1000 字符截断在 AC 前等

零产品代码变更；hook 强制层 0 改动、治理内核 0 触碰、fail-closed 语义不变。
实施从 T-0107 起按批准后的排布执行。

## 业务范围

### 批 1：全仓库设计漏洞排查（只读审计，不改代码）

审计范围（AST/正则/抽样深读三结合）：
- `loop_core/`（57 模块，重点 4 巨模块 + context_packager/context_loader/role_orchestrator）
- `hooks/scripts/`（15 脚本，重点 loop_enforcement.py 2059 行）
- `tools/`（36 个）+ `.zcode/tools/`（15 个）+ `scripts/`（24 个）

审计维度（每维度产出 文件:行号 证据）：
- **D1 截断类**：`[:N]` 切片、read_text 截断、`[:1000]` 类魔法值——是否截在语义边界前
  （如任务卡 AC 节、JSON 结构、报告结论）、截断后是否标记（truncated flag）、
  无提示静默截断
- **D2 魔法数值**：字符/行数/秒数上限散落硬编码、评分/阈值魔法数、exit code 语义不集中
- **D3 无界操作**：subprocess 无 timeout、递归扫描无深度/数量上限、读全文件无大小上限、
  循环无上限、重试无上限
- **D4 静默吞错**：except: pass、裸 except、失败后继续且无日志/无标记
- **D5 启发式推断**：正则/位置/顺序推断替代显式契约（如按名称/顺序匹配而非 schema 校验）

产出：`.ai/evidence/T-0106/audit-design-gaps.md` 分类清单：
- 修复项（正确性缺陷，进 T-0107）/ 优化项（性能/预算，进 T-0109）/ 合理项（文档化即可）
- context_packager 专项：≥5 处具体缺陷证据（1000 字符截断位置、字符 vs token、diff 无缓存、
  git 命令无 timeout 保护等）

### 批 2：BH 融合详细方案（设计文档，模块级）

覆盖特性（对应调研结论"BH 优于 LE 的 8 项"）：
1. **评估模型升级**：证据状态七态（Present/Wired/Exercised/Outcome-supported/Missing/
   Unobserved/N-A）引入 gate evidence；评分上限表（≤59/74/84/94/100）结构性防乐观；
   Repair Progress 与 Loop Effectiveness 分离（修复 GO ≠ 长期有效，等后续可比 Episode）
2. **单一数据源**：状态五写（state/task_graph/任务卡 Status/HANDOFF/PROGRESS）收敛为
   state.yaml 权威 + projection_engine 生成视图 + validate_state 新鲜度检查
3. **gates.yaml 分层瘦身**：active/archive 拆分 + forbidden_actions 模板外提为 policy 引用
   + gate_type 枚举化
4. **按需加载与文档路由**：.ai/README Switchboard（Owns/Does Not Own/Read Next）+
   目录四态（active/generated/target/candidate）+ 顶层 20+ 文档活/死归类
5. **工具层 capability 化**：tools/ 36 个按域分组、薄壳消除（委托 MCP server 注册表）、
   死工具删除、重复合并（dashboard 四层/证据链三处/安全扫描三处/缓存同步三处）、
   workflow/advanced/maintainer audience 分级
6. **上下文打包升级**：token 预算替代字符、任务卡 AC 节解析、git diff 缓存、
   subprocess 超时补齐
7. **评估产物契约化**：finding 结构化修复契约（expectedOutput/修复边界/验证命令/
   acceptance checks，对齐 BH harness-findings.input.json）
8. **治理契约测试**：.ai/ 文档链接完整性测试（仿 doc-link-graph）+ 投影新鲜度测试

每特性输出：目标文件/函数/新增模块 → 改动方式（新增/修改/删除）→ 依赖 → 风险 →
验收方式（测试/门禁）→ 与既有机制的关系（哪些必须保持：防篡改、fail-closed、审批闭环）

### 批 3：双方共同弱点优化方案（设计文档）

1. **巨型单文件拆分**（5 个 >50KB）：loop_enforcement.py 2059（控制流/约束表/白名单外提，
   **不拆主流程语义**，自愈 SHA+重执行机制不动）、governance_metrics 1508、intent_router 1484、
   human_review_packet 1307、context_loader 1342——每文件拆分边界 + 行为等价验收
2. **魔法数字集中化**：exit code、阈值、上限、评分天花板 → 常量表/配置（对齐 BH 上限表显式化）
3. **"修复器"现象治理**：repair_continuity 触发率度量（guard-events 加计数）、
   生成路径缺陷归类（是校验过严还是生成不稳）、修复器保留为确定性兜底

### 批 4：整合任务排布（T-0107~T-0111）

每任务输出：目标 / 范围 / AC 草案（可测）/ 依赖 / 风险与缓解 / 验收门 / 预计变更文件清单。
排布原则：风险从低到高、先收敛后分层、hook 强制层与内核全程不动、每任务独立 gate。

## 可验证验收标准

1. **[AC-01]** 设计漏洞排查报告落盘：覆盖 4 审计维度 × 4 代码域，每条证据含 文件:行号；
   分类为 修复项/优化项/合理项；context_packager 专项 ≥5 处具体缺陷
2. **[AC-02]** BH 融合方案覆盖 8 个特性，每个特性含 目标文件/改动方式/依赖/风险/验收方式；
   明确"哪些既有机制必须保持"（防篡改/fail-closed/审批闭环）
3. **[AC-03]** 共同弱点方案覆盖 3 项：巨模块拆分边界（行为等价验收）、魔法数字集中化清单、
   修复器治理度量方案
4. **[AC-04]** 整合任务排布 T-0107~T-0111：每任务含 AC 草案/依赖/风险/验收门/变更文件清单；
   排布遵循"风险从低到高、hook 与内核不动"原则
5. **[AC-05]** 排查中发现的**已确认修复项**在 KNOWN_ISSUES.md 登记（新问题可见、可追踪）
6. **[AC-06]** 设计文档与任务卡同步更新（T-0106 卡 + evidence/T-0106/ 完整）；
   git diff 实证：仅 .ai/ 变更，hooks/ 与内核零改动
7. **[AC-07]** 独立审查 GO（约束零弱化 + 设计真实性 + 排布可执行性）
