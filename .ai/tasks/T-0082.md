# T-0082: Loop 工程质量治理与运行时执行接管

## 任务概述

将 Loop 工程升级为具备"运行时执行接管 + 代码质量管控 + 软件工程项目质量管控"能力的系统。

| status | active |
| loop_mode | FULL |
| created_at | 2026-07-31T00:00:00+08:00 |
| max_files | 80 |

## 用户目标

1. 治理控制器可用：RuntimeController、Hook、Gate、权限边界全部正常运行
2. 运行时执行接管：主会话只负责编排/汇总/Gate 呈现，业务代码修改由 developer 子智能体执行
3. 代码质量管控：统一 QualityReport / SecurityReport，绑定 task/phase/gate/commit/diff fingerprint
4. 软件工程项目质量管控：分层质量门（编辑级/任务级/阶段级）、角色隔离、副作用授权
5. 治理事实源收敛：state/task/gate/phase/projection/evidence 交叉一致性
6. 真实角色子智能体执行：developer、quality-engineer、security-engineer、test-engineer、independent-reviewer 各自独立 actor/session

## 业务范围

- **IN SCOPE**:
  - RuntimeController 身份/授权/调度链路
  - 代码质量执行链（static_analyzer、security_scanner 接入）
  - 统一报告体系（QualityReport、SecurityReport）
  - 角色子智能体定义与独立 actor/session 隔离
  - 分层质量门（编辑级 / 任务级 / 阶段级）
  - 统一副作用权限控制
  - 治理事实源交叉一致性
  - 验收：端到端纵向切片验证

- **OUT OF SCOPE**:
  - 部署、回滚、数据库迁移、生产权限修改
  - 生产数据处理
  - 真实密钥/token/密码/生产凭据处理
  - 项目业务功能开发
  - 外部服务集成

## 禁止动作

- 不得修改项目业务代码（非治理相关源码）
- 不得通过 Node REPL、Python、Bash 或其他工具绕过 Hook
- 不得把主会话伪装成 developer
- 不得伪造 child session、receipt、ledger、evidence 或 verdict
- 不得将测试通过、validator PASS、reviewer PASS 当作用户 Gate 批准
- 不得在没有 active task 和 approved Gate 时修改实现
- 不得部署、迁移数据库、修改生产权限或处理生产数据
- 不得处理真实密钥、token、密码或生产凭据
- 不得一次性跳过阶段

## 可验证验收标准

1. **[AC-01]** 主会话直接写业务文件被阻断
2. **[AC-02]** 授权 developer 子会话可以在允许路径写入
3. **[AC-03]** Node REPL、Bash 重定向等旁路写入被阻断或完整审计
4. **[AC-04]** 安全缺陷导致 security BLOCKED
5. **[AC-05]** quality/security/test/reviewer 真实执行
6. **[AC-06]** developer/reviewer 共享 actor/session 时阻断
7. **[AC-07]** Host Adapter 不可用时不生成 takeover PASS
8. **[AC-08]** 旧 fingerprint 报告失效
9. **[AC-09]** state/task/gate/projection/evidence 漂移时阻断
10. **[AC-10]** 工具缺失、超时、非法输出时为 BLOCKED/NOT_VERIFIED
11. **[AC-11]** S1→S2→S4→S5→S6 纵向切片完整通过
12. **[AC-12]** S6 只提交人工 GO/NO-GO，不自动批准

## 风险和回滚策略

| 风险 | 等级 | 缓解 |
|------|------|------|
| RuntimeController 封锁主会话无法操作 | HIGH | 通过 Agent 子智能体建立合法 dispatching 通道 |
| Host Adapter 不可用导致 takeover 无法验证 | HIGH | 标记为 NOT_VERIFIED，不伪造 PASS |
| 修复过程中引入新漂移 | MEDIUM | 每个阶段结束生成 evidence 并验证交叉一致性 |
| 角色隔离机制与现有 hook 冲突 | MEDIUM | 先在 fixture 模式验证，再切换生产模式 |
