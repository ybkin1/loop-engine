## 2. 三要素设计

### 2.1 模板：`templates/stability/resilience-design.md`

**Part A — RT 治理顺序（面试题：50ms→5s 治理顺序）**
标准治理阶梯（每步必须可观测、可回滚）：
1. **止血**：先限流/熔断最劣调用（避免雪崩），5 分钟内恢复可用性
2. **定位**：链路拆分定位（网关→服务→DB→第三方），p50/p95/p99 分位对比
   （面试题：何时看平均、何时看分位 —— 平均掩盖长尾，p99 反映体验）
3. **根因**：慢 SQL / 锁等待 / GC / 依赖抖动 四类优先排查
4. **根治**：索引/缓存/异步/扩容 四选
5. **验证**：恢复后持续观察 24h 指标基线

**Part B — 熔断阈值与恢复策略（面试题：阈值与恢复）**
- 熔断触发三要素（缺一不可）：错误率阈值（如 ≥50% 持续 10s）+
  最小请求量（如 ≥20 req/s 防冷启动误判）+ 窗口期
- 半开恢复：等待窗口（如 30s）→ 放行 10% 试探流量 → 成功率达阈值
  （如 ≥80%）→ 全开；失败 → 重新熔断（指数退避）
- 阈值推导方法：基于 SLO/error budget 反推（与引擎 T-0090/T-0093 SLO
  子系统对齐），不拍脑袋
- 快失败超时：调用方超时 ≤ 下游 p99 的 50%（防排队堆积）

**Part C — 降级恢复判定（面试题：如何判定已恢复）**
- 三层判定：① 熔断器状态（半开→全开）② 业务指标（错误率/RT 回到 SLO
  基线并稳定 30 分钟）③ 依赖健康（下游恢复探针）
- 恢复≠回切：先低流量回切（1%/10%），观察后再全量

### 2.2 角色知识

**归属角色：system-architect（稳定性设计）+ release-engineer（发布前验证）**
+ **quality-engineer（降级演练）**

`agents/system-architect/references/resilience-checklist.md`：
- 架构评审必问：核心链路熔断/限流/降级三件套是否齐备、阈值如何得出
- 降级方案必须列出「降级后用户体验是什么」（业务无感知/降级感知二选一）

`agents/release-engineer/references/resilience-release-checklist.md`：
- 发布前：熔断配置存在 + 阈值推导文档 + 降级演练记录（复用引擎 T-0129
  防御演练 E1~E5 模式）

### 2.3 门禁检查点

1. [CHECK] 核心接口有熔断配置（错误率阈值 + 最小请求量 + 半开恢复窗口）
2. [CHECK] 阈值推导文档存在（基于 SLO 反推或基线数据）
3. [CHECK] 降级演练记录（注入故障 → 验证降级 → 恢复判定）
4. [CHECK] 超时配置 ≤ 下游 p99 的 50%（防排队雪崩）
