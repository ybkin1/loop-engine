## 2. 三要素设计

### 2.1 模板：`templates/performance/performance-diagnosis.md`

**Part A — 长尾延迟定位（面试题：RT 正常但 p99 很慢）**
- 分位指标选择（面试题：何时看平均、何时看分位）：
  | 场景 | 用哪个指标 |
  |---|---|
  | 系统容量规划/资源预估 | 平均（吞吐相关） |
  | 用户体验/线上告警 | p99/p999（长尾感知） |
  | 压测合格判定 | p99 + 拐点 |
- 定位四步：
  1. 按分位切分请求（p50/p90/p99/p999 分组）
  2. 长尾样本抓取（慢请求日志 + 采样）
  3. 维度下钻：接口→服务→DB/第三方→GC/锁
  4. 长尾根因四类：慢 SQL / 锁等待（DB 锁、分布式锁）/ GC 停顿 / 依赖超时
- 工具：链路追踪（trace ID 贯穿）+ 慢请求采样

**Part B — 慢 SQL 优化（面试题：2s→20ms + 11 亿行）**
- 优化手段阶梯：
  1. **看执行计划**（EXPLAIN）：确认 type（ref/range 而非 ALL）、扫描行数、
     是否 filesort/temp table
  2. **索引确认用上**（面试题：怎么确认索引被用上）：EXPLAIN 的 key 字段
     显示实际使用的索引 + 强制索引对比 + 索引选择性验证
  3. 覆盖索引（避免回表）+ 联合索引顺序（最左前缀）
  4. 分页优化（深分页 offset 大 → 游标/延迟关联）
  5. 写放大/锁竞争：批量写、避免行锁长时间持有
  6. 最终手段：读写分离 / 分库分表
- **11 亿行场景**（面试题：方案还成立吗）：
  - 索引优化依然成立，但收益递减；必须考虑：分区表、冷热分离
    （归档热数据）、数据生命周期策略
  - 全表扫描类操作（count/大聚合）不再可行 → 计数表/汇总表/异步统计

**Part C — GC 排查（面试题：频繁 GC 怎么排查）**
- 排查四步：GC 日志开启 → 观察 Full GC 频率与停顿 → 堆转储分析
  （大对象/内存泄漏）→ 根因归类
- 常见根因：大对象频繁创建、缓存无界、连接/流未关闭、反射/动态代理
- 与长尾关联：GC 停顿直接贡献 p99 长尾（Part A 联动）

### 2.3 门禁检查点

2. [CHECK] 慢 SQL 清单 + explain 分析记录存在
3. [CHECK] 索引使用确认证据（explain key 字段截图/记录）
4. [CHECK] 长尾定位记录（慢请求采样 + 根因归类）

## 5. 风险

| 风险 | 缓解 |
|---|---|
| 诊断知识随 DB 厂商差异 | 模板以标准 SQL/通用方法论为主，厂商特性标注示例 |
| 检查点要求过高 | 按项目规模分级（小项目仅要求报告，大项目要求证据） |
| 与 deep_probe 混淆 | 明确：deep_probe 查引擎自身探针；本模板面向交付项目的性能诊断 |
