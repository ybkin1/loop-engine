## 0. 摘要：从「流程治理」转向「质量治理」

用户明确批评：当前 loop 工程**重流程、轻质量，本末倒置**——gate 审批、
自我锁死、每次都要人开 gate，但没看到项目质量因此提高。

本设计的立场转变：

| 旧（流程导向） | 新（质量导向） |
|---|---|
| 流程正确性 = 目标 | 产物正确性 = 目标，流程只是手段 |
| gate = 人审批关卡（每次卡人） | 质量门 = 机器自动判定（达标放行） |
| 评审 = 关卡（不通过不让走） | 评审 = 反馈环（发现问题→自动返工→复验） |
| 防 AI 违规（防绕过） | 让 AI 交付质量（信任 + 自动验证） |
| 人介入 = 每个流程节点 | 人介入 = 仅价值决策点（需求歧义/取舍/边界/目标冲突） |

核心主张（用户原话的展开）：**人的研发团队能做到的事，AI 都能做到**——
不是 AI 能力问题，是 agent 组织形态问题。本设计把 pi agent 定制为
「质量环驱动的软件研发团队」，而不是「流程关卡流水线」。

## 1. 质量维度全景（发散补充：远不止用户列的那些）

用户列举了：代码风格、脏东西、测试质量、前后逻辑/因果、AI 偷懒。
完整全景（每维：定义 / AI 特有缺陷信号 / 检测方式 M=机器 L=LLM T=实测）：

| # | 维度 | AI 特有缺陷信号（偷懒/幻觉/编造的具体表现） | 检测 |
|---|------|-------------------------------------------|------|
| 1 | **功能正确性** | 只实现 happy path；mock 掉真逻辑；魔法值硬编码期望结果 | T/L |
| 2 | **完整性** | AC 漏做；文档/测试/契约没同步更新；需求↔实现断链 | M/L |
| 3 | **一致性（因果链）** | 改了 A 的契约没改 B 的调用；复制粘贴后没改完；命名漂移 | M/L |
| 4 | **健壮性** | 异常被吞掉；边界不处理；并发竞态；资源泄漏；输入不校验 | L/T |
| 5 | **安全性** | 密钥硬编码；SQL/HTML 拼接；绕过认证；依赖带洞 | M/L |
| 6 | **性能** | O(n²) 循环；重复计算；无缓存；同步阻塞热点 | L/T |
| 7 | **可维护性** | 巨型函数；意大利面条；魔法数字；注释说谎；重复代码 | M/L |
| 8 | **可测试性** | 测试只测自己实现；断言过弱；测试依赖顺序；mock 掉一切 | M/L |
| 9 | **可扩展性** | 接口写死；无配置化；模块耦合；扩展需要改核心 | L |
| 10 | **可观测性** | 无日志；错误被吞；无指标；出问题不可诊断 | L |
| 11 | **可部署性** | 构建不可复现；配置散落；缺迁移脚本；环境不一致 | M/L |
| 12 | **兼容性** | 依赖版本随意升；API 破坏性变更；平台差异不处理 | M/L |
| 13 | **数据质量** | 数据不校验；迁移丢数据；缓存与存储不一致 | L/T |
| 14 | **文档质量** | 文档与代码行为不符；API 文档缺失；注释过期 | M/L |
| 15 | **代码卫生** | 调试残留；死代码；TODO 泛滥；文件膨胀 | M（零成本） |
| 16 | **交付质量** | 版本不一致；产物不完整；发布清单缺失 | M |

**设计含义**：这张全景表就是「评审检查清单」的来源——每个维度要么有
机器检查器（M），要么有专门视角的 auditor（L），要么靠可执行验证（T）。
任何产出（代码/文档/配置/测试）都要过这张表，而不是只有"代码风格"。

## 2. 方案设计：质量环（Quality Loop）—— 比"多 agent 流水线"更好的形态

### 2.1 为什么不是"多角色顺序审查"

多角色顺序审查（安全看完质量看）的问题是：贵（每轮一串 LLM 调用）、慢、
角色间无信息共享（各自从头看代码）、顺序依赖。更好的形态：

**① 证据分层：机器事实层 + LLM 判断层**
```
L1 机器验证（零成本，写入即触发）：语法/lint/密钥/注入/调试残留/死代码/规模
L2 可执行验证（低成本，产物必须自带）：验证方案（测试/命令/断言）→ 机器执行 → 证据文件
L3 LLM 多视角会诊（按需）：auditor 组共享 L1/L2 证据 + 代码，一次会诊产出多视角发现
```
LLM 的判断（L3）**必须基于机器证据（L1/L2）**——这从机制上消灭"编造验证"：
评审不能"我觉得没问题"，必须引用验证证据。

**② 可验证性设计（Verifiability-by-Design）—— 防偷懒/编造的最强机制**
不是"AI 做完后让人/LLM 检查"，而是**要求每个产出必须附带验证方案**
（如何证明做对了：测试命令、断言、复算脚本），然后**机器自动执行验证方案**。
- 偷懒（没做/做一半）→ 验证方案执行失败或无证据
- 编造（假装做了）→ 验证证据不存在或与声明不符
- 做多了（scope creep）→ 验证方案覆盖不了，追溯矩阵暴露多余产出

**③ 追溯矩阵（Traceability Matrix）—— 因果链的机器化**
```
需求/AC ──→ 实现（diff 文件/函数）──→ 测试（用例名）──→ 文档（引用）
```
每个任务自动生成矩阵；断链（需求没实现/测试没覆盖/文档没更新）→ 机器检测。
这同时防三类：偷懒（断链）、做多（矩阵外产出）、因果断裂（改了实现没改文档）。

**④ 质量环（不是流水线）**
```
任务 → [L1/L2 自动验证] → [L3 会诊] → 达标 → 放行（自动，无需人）
                        ↘ 不达标 → 自动生成返工单 → executor 修复 → 回到验证
持续不达标（N 轮）→ 升级人（此时是真实的价值决策，不是流程关卡）
```
- gate 从"人审批"退化为"质量门自动判定"：任务批准后执行自动进行，质量达标
  自动 done——**人不再被流程卡住**
- 人的介入点只有 4 类价值决策：需求歧义、目标取舍、外部边界、目标冲突
  （沿用升级协议思想，但触发条件从"流程卡点"变为"价值决策点"）

**⑤ 对抗性立场（Agent Adversarial Design）**
不是"友好的多角色"，而是**有立场的对抗**：
- executor 立场：把需求做出来（倾向"完成了"）
- auditor 立场：找茬（质量/安全/健壮性/一致性各自的角度，倾向"有问题"）
- orchestrator 立场：中立——**用机器证据裁决**，不靠口头辩论
立场冲突由 L1/L2 证据裁决，而不是人裁决——这就是"团队复审"的 agent 版，
且不依赖人的精力。

## 3. Pi agent 定制设计（发挥到最大）

### 3.1 Pi 独有能力 → 质量环的落点

| Pi 能力（已有实现） | 在质量环中扮演 |
|---|---|
| subagent-v2（3 层递归/parallel/chain/深度护栏） | executor 派发 + auditor 会诊并行派发 |
| 会话持久化（--session 显式路径） | 角色级记忆的载体（每角色独立会话文件） |
| memory 扩展（目录即记忆库，项目库+用户库） | 项目记忆 + **角色级记忆** + 缺陷模式库 |
| mini-loop v2（gate/validate/证据锚定/事件溯源） | 质量环状态机（改造 gate 为自动质量门） |
| quality-actions（写后静态检查） | L1 层（扩展检查项） |
| 1M 上下文（deepseek-v4-pro/flash） | 多视角会诊一次装下全部证据 |
| agent-bridge（微信） | 可选：移动端质量反馈通道 |

### 3.2 角色矩阵（专业视角型团队，替换"执行型 4 角色"的定位）

| 角色 | 专业视角 | 立场（fixed stance） | 边界 | 否决权 | 角色级记忆 |
|------|---------|---------------------|------|--------|-----------|
| **orchestrator** | 质量环调度 | 中立：机器证据裁决 | 不实现不评审 | — | 项目目标/进度/质量趋势 |
| **executor**（worker） | 实现 | "把需求做出来并附验证方案" | 不评审自己的产出 | — | 实现模式/踩坑 |
| **quality-auditor** | 可维护性/代码质量/测试质量 | "找茬：可读性/结构/测试有效性" | 只评审不修改 | 质量缺陷打回 | 代码味道/测试反模式库 |
| **security-auditor** | 安全性 | "找茬：任何不安全都打回" | 只评审 | 安全 P0 必打回 | 漏洞模式库 |
| **robustness-auditor** | 健壮性/边界/异常/并发/资源 | "找茬：假设验证" | 只评审 | 健壮性缺陷打回 | 边界案例库 |
| **consistency-auditor** | 因果/契约/追溯/偷懒/做多 | "找茬：声称 vs 事实" | 只评审 + 对照机器证据 | 断链打回 | 历史断链案例 |
| **performance-auditor** | 性能（按需触发） | "找茬：复杂度/资源" | 只评审 | 严重性能问题打回 | 性能反模式库 |
| **verifier**（工具化，非 LLM） | 机器验证执行 | 无立场（确定性） | L1/L2 执行 | 证据缺失即不通过 | — |

**会诊模式**：orchestrator 一次并行派发多个 auditor（subagent parallel），
共享 L1/L2 证据 + 代码 + 追溯矩阵，各自输出结构化发现
（`{severity, dimension, evidence_ref, file, fix_suggestion}`）→ 汇总裁决。

### 3.3 记忆设计（遗忘曲线对抗）

```
.pimemory/
├── roles/<role>/         角色级记忆（每个 auditor 自己的经验）
│   ├── findings/         本角色历史发现（类型/模式/修复方法）
│   └── standards/        本角色的检查清单（随经验演化）
├── defects/              缺陷模式库（本项目踩过的坑，注入新任务评审）
├── project/              项目知识（架构/契约/决策）
└── user/                 用户偏好
```
- 每次会诊的发现 → 沉淀到 roles/<role>/findings + defects/（增量学习）
- 新任务评审时自动注入相关缺陷模式（"本项目上次这类问题出在 X"）
- 角色级记忆是**人的团队经验的 agent 等价物**——这是当前 loop 工程完全没有的

### 3.4 追溯矩阵与验证方案的实现形态

- 任务卡新增字段（mini-loop tasks.json v2 扩展）：
  ```json
  { "ac": ["AC-01 描述", ...],
    "verification": ["node --test tests/x.test.js", "curl -s localhost:8080/health | jq .status"],
    "trace": { "AC-01": { "impl": ["src/x.js:12"], "tests": ["test_x"], "docs": ["docs/x.md"] } } }
  ```
- executor 完成时填写；verifier 执行 verification 命令 → `verification-evidence.json`
  （机器证据，哈希锚定——复用 mini-loop 的 evidence 机制）
- consistency-auditor 校验 trace 矩阵断链（ac 有实现无测试 → 断链；实现无 ac → 做多）
- 质量门判定 = L1 全过 + L2 证据齐全且通过 + L3 无 P0/P1 阻断 → 自动放行

### 3.5 与现有 mini-loop v2 的整合（不推翻，改造语义）

- gate 语义改造：任务批准后**执行自动进行**（trust mode），不再每步卡人；
  gate 记录质量门判定结果（`quality_gate: auto_pass | rework | escalated`）
- 事件溯源保留：质量环的每一轮（验证/会诊/返工/放行）都入 events.jsonl
- validate 扩展：质量环状态校验（证据缺失/验证未执行 → fail-closed）
- 反幻觉闸门升级：评审必须引用 L2 证据文件（无证据引用 → 无效评审）
- 3 轮上限保留：持续不达标才升级人（价值决策）

### 3.6 一个任务的质量环走查（示例）

```
用户：/task-start T-020 增加登录限流（带 ac + 期望验证方式）
orchestrator：解析任务 → executor 派发（含 AC/验证要求/项目上下文/相关记忆）
executor：实现 + 填写 trace 矩阵 + 附验证方案 → 提交
verifier（L2）：执行验证方案 → 证据文件（通过/失败）
L1：quality-actions 检查（写入即触发）
consistency-auditor + quality-auditor + security-auditor（并行会诊）：
  基于代码 + L1/L2 证据 + 矩阵 → 发现（如：限流未覆盖登录接口的 X 分支 + 测试只测了 happy path）
orchestrator：汇总 → 有阻断 → 自动生成返工单 → executor 修复 → 复验
  复验通过 → 质量门自动放行 → done（无需用户审批）
用户只在：需求歧义（限流阈值多少？）或 3 轮不达标时介入
```

## 5. 路线图

| 期 | 内容 | 价值 |
|----|------|------|
| **P0**（先做） | L1 补全（quality-actions 扩展：调试残留/TODO/死代码/规模/密钥）+ 任务卡 verification 字段 + verifier 执行器 + 反幻觉升级（必须引用验证证据）+ quality-auditor 首秀 | 直接消灭"偷懒/编造"的两大漏洞 |
| **P1** | auditor 角色组（security/robustness/consistency）+ 并行会诊 + 角色级记忆 + 缺陷模式库 + mini-loop 质量门自动判定 | 团队复审形态 + 经验积累 |
| **P2** | performance-auditor + 追溯矩阵自动化 + 跨项目缺陷模式复用 + 质量仪表盘（维度分数/趋势） | 全维度覆盖 + 质量可度量 |

**P0 是最小可用质量环**：一个 auditor + 验证证据 + 自动返工，就能让用户
看到"质量真的提高了"（有证据、有自动返工、不用人审批）。

## 6. 边界与诚实声明

- 本设计为 candidate，**不落地代码**（Pi 侧实现为独立任务，需用户 gate）
- 承认上限：机器 + LLM 无法证明软件无 bug（理论边界）；目标是
  **检出率最大化 + 漏检必留痕 + 修复自动闭环**
- 不否定现有治理的防绕过价值（hooks/防编造/范围控制保留），但 gate 从
  "人审批关卡"退化为"质量门自动判定"——**流程让位给质量**
- 与并行会话（Qoder T-0167）不冲突：本设计聚焦 Pi + LLM 判断层，OQA-4D
  聚焦 Qoder + 机器检查层
