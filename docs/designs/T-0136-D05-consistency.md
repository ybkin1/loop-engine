## 2. 三要素设计

### 2.1 模板：`templates/consistency/consistency-design.md`

**Part A — 缓存一致性（面试题：先删缓存 vs 先更新库）**
- 两种方案对比：
  | 方案 | 风险 | 适用 |
  |---|---|---|
  | 先删缓存再更新库 | 删缓存后、更新库前有读请求 → 读旧值回填 → 缓存长期脏 | 写少读多、容忍短脏 |
  | 先更新库再删缓存 | 更新后删除失败 → 缓存保留旧值 | 业界主流 |
  - 先更新库再删缓存的**补偿**：延迟双删（删→延时→再删）+ 消息重试删除
- 强一致场景（面试题：什么业务强一致）：支付/账务/库存扣减 → 直接读库
  或分布式锁串行化，不经过缓存
- 最终一致场景：读多写少的展示类数据（商品详情/用户资料）→ 缓存 +
  异步失效 + 对账兜底

**Part B — 异步化取舍（面试题：哪些可异步/哪些必须同步）**
- **必须同步**：强一致写（支付扣款）、需要实时回执的读（用户感知核心）、
  事务边界内
- **可异步**：非实时通知（邮件/短信/推送）、可延迟的处理（报表/统计/
  计费对账）、可补偿的副作用（积分/日志/审计）
- 异步化的代价应对（面试题：用户感知与数据一致性）：
  - 用户感知：立即返回「受理成功」+ 进度查询接口 + 最终结果通知
  - 数据一致性：消息不丢 + 幂等 + 对账补偿（见 Part C/D）

**Part C — 消息不丢失（面试题：如何保证不丢 + MQ 丢了怎么办）**
- 三层不丢：
  1. 生产端：confirm 机制（发送确认）+ 本地消息表（未确认重发）
  2. MQ 端：持久化（刷盘策略）+ 副本（集群高可用）
  3. 消费端：手动 ack（处理成功才 ack）+ 死信队列（重试 N 次后进 DLQ）
- **MQ 本身丢消息**（面试题）：降级方案 = 本地消息表兜底（业务库内记录
  事件状态，MQ 仅作传输，对账任务扫描未完成事件重发）
- 对账兜底：定时任务比对「业务表状态 vs 消息消费状态」，不一致补偿

**Part D — 幂等设计（面试题：生产端/消费端幂等）**
- 生产端幂等：消息唯一 ID（业务键派生）+ 发送前查重（本地消息表状态）
- 消费端幂等：业务唯一键（订单号/流水号）+ 消费记录表唯一约束 +
  处理结果可重放（状态机幂等：同状态更新不重复副作用）
- 判断幂等是否满足：重放同一条消息 N 次，业务结果与执行 1 次一致
