## 2. 三要素设计

### 2.1 模板

**模板 A：`templates/architecture/ddd-split-guide.md`（DDD 与微服务拆分）**
- DDD 核心概念速查：限界上下文（Bounded Context）/聚合/领域事件/
  防腐层（ACL）/事件风暴
- 何时用 DDD：业务规则复杂、多团队边界模糊、领域知识密集；
  何时不用：CRUD 型应用、团队规模小（避免过度设计）
- 微服务拆分决策表：
  | 拆分信号 | 说明 |
  |---|---|
  | 团队规模 | 2 pizza 团队规则 |
  | 变更频率 | 独立发布诉求 |
  | 数据边界 | 能否独立拥有数据 |
  | 失败隔离 | 单点故障影响面 |
- 拆分顺序：先限界上下文 → 再数据边界 → 再服务边界 → 接口契约先行

**模板 B：`templates/deployment/release-strategy-guide.md`
（灰度/蓝绿/金丝雀场景决策）**
| 策略 | 适用场景 | 不适用 |
|---|---|---|
| 灰度发布 | 用户量可切分、需按用户维度放量观察（功能开关） | 数据不可分割 |
| 蓝绿发布 | 环境切换快、需整体回滚（数据库兼容双版本） | 大版本不兼容变更 |
| 金丝雀 | 新版本风险高、小流量验证（按比例/按特征） | 无监控体系 |
- 决策输入：变更风险等级 + 回滚能力 + 数据兼容性 + 可观测性

### 2.2 角色知识

**归属角色：system-architect（DDD/拆分决策）+ release-engineer
（发布策略选择）+ delivery-manager（排期冲突处理）**

`agents/system-architect/references/ddd-checklist.md`：
- 拆分前必答四问（团队/变更/数据/隔离），答案留档

`agents/delivery-manager/references/tradeoff-checklist.md`
（面试题：1 个月 vs 2-3 个月改造）：
- 需求排期冲突处理范式：
  1. 拆解：找出 1 个月内可达的最小可交付切片（MVP 切分）
  2. 对齐：向用户呈现「完整改造 vs 分期」的取舍（升级协议第 1 类
     产品取舍，选择题形态）
  3. 兜底：技术债登记（KNOWN_ISSUES）+ 后续任务排布
- 技术债优先级（面试题：老系统不能改怎么排）：
  P0 安全/数据风险 > P1 稳定性（故障面） > P2 性能 > P3 维护性；
  无法修改的老系统 → 隔离 + 监控 + 封装（防腐层），不强行重构

## 3. AI 能力边界方法论（面试题 #18 专项设计）

> 本节内容即「AI 边界方法论」主体；T-0142 落地时将其拆出为独立文档
> `docs/designs/T-0136-D06-ai-boundary.md` 并纳入角色 references
> （当前为设计内小节，独立文档待落地任务创建，非现存文件）。
- **AI 可替代/增强环节**（引擎已有实践可外推）：
  - 代码生成/重构/测试生成 → developer/test-engineer（已落地）
  - 审查辅助/模式识别 → independent-reviewer（已落地）
  - 文档/报告生成 → tech-writer 角色（评估中）
  - 容量估算/压测分析 → 数据驱动模板（本方案 D-01 落地后 AI 可执行）
- **必须工程能力（AI 无法替代）**：
  - 用户价值判断与取舍（升级协议 4 类场景，EVIDENCE_ONLY_BOUNDARY）
  - 规则层/权限/安全边界裁决（USER_AUTHORITY 不可代理）
  - 生产数据/真实业务项目的最终操作（外部边界 gate）
  - 故障时的止损决策（演练预案内可 AI 执行，预案外须人工）
- 判定准则：**可复算可验证 → AI 可增强；不可复算的价值/风险裁决 → 人**
  （与引擎「机器可验证链」原则一致）
