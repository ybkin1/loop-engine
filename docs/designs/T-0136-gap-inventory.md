## 4. 根因分析

Loop 工程成长史（T-0082~T-0135）全部为**治理自举**（把 Loop 自己管好）：
gate/证据/审查/状态机/委托链。领域知识层只有「架构/发布/安全/测试」四角色
有实质方法论。后端工程核心知识（容量、稳定性、性能、数据）尚未以
「可复用模板 + 角色知识 + 门禁检查」形态沉淀 —— 与「接管所有 ZCode 项目」
的角色定位存在结构性缺口。

## 5. 补全原则（约束后续设计）

1. **三要素最小交付**：每域 = 模板（可直接填用）+ 角色知识（哪个角色负责、
   何时触发、怎么裁决）+ 门禁检查点（发布前强制校验项），不做大而全
2. **候选分域分批**：P0 先行（T-0137 容量压测 / T-0138 稳定性 / T-0139
   数据迁移），P1 其次（T-0140 性能诊断 / T-0141 一致性设计），P2 收尾
   （T-0142 架构与方法），每批独立 gate 批准
3. **不触碰既有资产**：只新增模板/知识/检查点设计，不改 hooks/内核/产品代码
4. **可验证**：每域设计的门禁检查点必须可被脚本或 checklist 验证
