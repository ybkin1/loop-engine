# Loop 工程 12 阶段规范

> 本文是 12 个软件工程阶段的权威规范。每个阶段定义：目标、入口条件、角色分工、强制产出、退出条件、人工评审点。

---

## S0: Init — 项目初始化

| 维度 | 内容 |
|------|------|
| **目标** | 建立治理骨架，使项目进入可管控状态 |
| **入口条件** | 项目根目录存在 |
| **角色** | main-thread（编排） |
| **强制产出** | `.ai/state.yaml`, `.ai/gates.yaml`, `.ai/task_graph.yaml`, `.ai/HANDOFF.md` |
| **退出条件** | 四份治理文件全部存在且 validate_state 通过 |
| **人工评审** | **无**——纯自动化 |

---

## S1: Requirements — 需求分析

| 维度 | 内容 |
|------|------|
| **目标** | 将用户模糊意图转化为可验证的需求规格 |
| **入口条件** | S0 完成，loop_mode 已确定 |
| **角色** | product-manager（需求澄清）、project-manager（范围管理） |
| **强制产出** | `docs/01-requirements.md`（含 FR/NFR/AC）、范围边界声明 |
| **退出条件** | 需求文档通过 product-manager 自检 + 无不可验证目标 |
| **🤚 人工评审** | **必须**——用户确认需求范围、优先级、验收标准。未批准前不得进入 S2 |

---

## S2: Architecture — 架构设计

| 维度 | 内容 |
|------|------|
| **目标** | 产出可机验的系统架构设计 |
| **入口条件** | S1 需求已批准 |
| **角色** | system-architect（整体架构）、module-architect（模块拆分） |
| **强制产出** | `docs/02-architecture.md`（13 项必填）、模块清单、依赖图 |
| **退出条件** | 架构文档通过架构合规检查（content_guard 验证模块结构） |
| **🤚 人工评审** | **必须**——用户确认技术选型、模块边界。未批准前不得进入 S3 |

---

## S3: Interface — 接口契约

| 维度 | 内容 |
|------|------|
| **目标** | 定义所有模块间接口契约，可机验 |
| **入口条件** | S2 架构已批准 |
| **角色** | module-architect（接口定义）、system-architect（跨模块一致性） |
| **强制产出** | `docs/03-interface-contract.md`（函数签名、数据结构、错误语义） |
| **退出条件** | `validate_contract.py` 通过（契约 vs 代码一致性） |
| **🤚 人工评审** | **可选**——复杂接口建议人工确认 |

---

## S4: Implementation — 代码实现

| 维度 | 内容 |
|------|------|
| **目标** | 严格按架构/接口实现功能代码 |
| **入口条件** | S3 接口契约已批准（或跳过），S2 架构已批准 |
| **角色** | developer（编码）、content_guard（机器拦截） |
| **强制产出** | 源代码 + 单元测试 |
| **退出条件** | content_guard 通过（ruff lint + 密钥扫描 + 架构合规） |
| **🤚 人工评审** | **无需**——机器拦截已涵盖编码规范、密钥、架构合规 |

---

## S5: Quality — 质量验证

| 维度 | 内容 |
|------|------|
| **目标** | 独立验证代码质量和功能正确性 |
| **入口条件** | S4 代码完成，compile gate 通过 |
| **角色** | quality-engineer（质量门禁）、test-engineer（测试执行）、security-engineer（安全扫描）、independent-reviewer（独立审查） |
| **强制产出** | 质量报告、测试报告、安全报告、独立审查报告（均需独立子代理会话证据） |
| **退出条件** | 四项报告全部通过 + subagent_evidence_verifier 5 层验证通过 |
| **🤚 人工评审** | **必须**——用户审查质量/测试/安全/Review 四项报告。任何一项 FAIL → 打回 S4 |

---

## S6: Delivery — 交付准备

| 维度 | 内容 |
|------|------|
| **目标** | 确保交付物完整、可复现、有回滚方案 |
| **入口条件** | S5 质量全部通过 |
| **角色** | delivery-manager（交付完整性）、release-engineer（部署/回滚） |
| **强制产出** | 交付清单、部署方案、回滚方案、版本号一致性验证 |
| **退出条件** | 交付清单全部打勾 + validate_state 通过 |
| **🤚 人工评审** | **必须**——用户最终接受。这是项目级 GO/NO-GO 决策 |

---

## S7: Integration — 集成验证

| 维度 | 内容 |
|------|------|
| **目标** | 验证模块间集成正确性 |
| **入口条件** | S5 或 S6 完成 |
| **角色** | test-engineer（集成测试）、system-architect（集成架构） |
| **强制产出** | 集成测试报告、跨模块调用链验证 |
| **退出条件** | 集成测试全部通过 |
| **🤚 人工评审** | **可选**——复杂集成建议确认 |

---

## S8: Functional Test — 功能测试

| 维度 | 内容 |
|------|------|
| **目标** | 端到端功能验证 |
| **入口条件** | S7 集成通过 |
| **角色** | test-engineer（E2E 测试）、quality-engineer（质量判断） |
| **强制产出** | E2E 测试报告、功能覆盖矩阵 |
| **退出条件** | E2E 测试通过 + 需求覆盖 100% |
| **🤚 人工评审** | **可选** |

---

## S9: Fix & Optimize — 修复与优化

| 维度 | 内容 |
|------|------|
| **目标** | 修复缺陷、优化性能 |
| **入口条件** | S8 测试完成且有缺陷发现 |
| **角色** | developer（修复）、quality-engineer（回归验证） |
| **强制产出** | 修复记录、回归测试报告 |
| **退出条件** | 所有 P0/P1 缺陷修复 + 回归通过 |
| **🤚 人工评审** | **可选** |

---

## S10: Performance — 性能验证

| 维度 | 内容 |
|------|------|
| **目标** | 验证性能指标达标 |
| **入口条件** | S9 完成 |
| **角色** | test-engineer（性能测试）、system-architect（瓶颈分析） |
| **强制产出** | 性能测试报告、瓶颈分析 |
| **退出条件** | 性能指标满足 NFR |
| **🤚 人工评审** | **可选** |

---

## S11: Maintenance — 持续维护

| 维度 | 内容 |
|------|------|
| **目标** | 持续监控、修复、迭代 |
| **入口条件** | S10 完成 |
| **角色** | developer + quality-engineer（持续集成） |
| **强制产出** | 变更日志、版本记录 |
| **退出条件** | 持续（无终止条件） |
| **🤚 人工评审** | **按需** |

---

## 人工评审汇总

| 阶段 | 评审要求 | 不评审的后果 |
|------|---------|------------|
| S1 需求 | **必须** | 需求不清 → 后续全部返工 |
| S2 架构 | **必须** | 架构偏离 → 代码不合规 |
| S3 接口 | 可选 | 接口冲突风险 |
| S4 实现 | 无需 | 机器已拦截 |
| S5 质量 | **必须** | 质量不达标 → 交付风险 |
| S6 交付 | **必须** | 最终 GO/NO-GO |
| S7-S11 | 可选/按需 | 低风险 |

> **规则：** 标记为"必须"的阶段，gate 在批准前必须有人工确认。session_brief 在会话启动时注入待评审提醒。
