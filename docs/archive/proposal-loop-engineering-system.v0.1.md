本文件是对当前沟通形成的完整设计提案。它记录设计理解、目标架构、角色体系、交付流程、质量控制、风险和缺口，不代表产品定义已经通过用户验收，也不代表任何安装、激活、runtime、agent、automation、protocol、tool 或 real-project entry 已获授权。

## 1. 执行摘要

### 1.1 要解决的根本问题

用户不是程序员，也不具备项目管理、架构设计、代码评审、测试工程、信息安全、部署运维等专业能力。要求用户逐行检查 AI 生成的代码，或者要求用户判断一个架构、测试和安全方案是否专业，都是不现实的。

当前市场上的 AI 编程工具通常可以很快生成一个视觉上完整、语言上合理、局部可以运行的 demo，但不能天然保证：

- 需求没有被误解；
- 产品范围没有漂移；
- 系统架构可以长期演进；
- 模块边界和接口合理；
- 函数职责清晰；
- 依赖关系没有形成隐性耦合；
- 编码规范被持续执行；
- 安全边界没有被绕过；
- 测试真正覆盖用户行为和失败路径；
- 构建、部署、监控和回滚可以工作；
- 代码在下一轮修改后仍然可维护。

因此，问题不是“如何让一个 AI 更会写代码”，而是：

> 如何把传统软件工程团队的职责、规范、设计、评审、测试、质量保证、交付和持续迭代机制，编排成一套 AI 可以执行、相互制约、可验证、可追溯、可交付的软件生产系统。

### 1.2 项目最终目标与当前设计对象

项目最终目标以 `.ai/PROJECT.md` 为准：帮助无代码能力、无项目管理背景的用户，借助 Codex 和 Loop 工程方式，从粗略需求推进到真实可用、可部署、可验收、可持续迭代的软件产品交付。

本文件讨论的是实现这一目标所需要的 Loop 工程系统。`loop-engine-lab` 是否最终成为一个真实、可用、可交付的 Loop 软件交付系统，属于产品身份提案和后续决策，不在本文件中自动批准。

### 1.3 核心结论

如果 Loop 只有以下循环：

```text
AI 写文档或代码
-> AI reviewer 评审
-> AI repair 修复
-> AI 输出 PASS
```

那么它只是提示词和文档的自我循环，不是完整的软件工程。

可靠的 Loop 必须同时具备：

```text
用户目标
-> 产品需求
-> 系统和模块架构
-> 任务与接口契约
-> 受约束实现
-> 确定性质量检查
-> 独立代码与架构评审
-> 修复和回归验证
-> 发布与运行检查
-> 用户对产品结果的确认
```

AI 角色负责专业判断和工程工作，确定性工具负责重复、客观、可重现的检查，主控负责边界和证据，用户负责目标、关键取舍、Gate 和产品结果确认。

## 2. 用户问题与成功定义

### 2.1 用户不承担技术验收责任

用户可以确认：

- 软件是否解决了实际问题；
- 使用流程是否符合预期；
- 业务规则是否正确；
- 重要取舍是否符合意图；
- 是否接受已知成本和风险。

用户不应被要求确认：

- 函数是否应该拆分；
- 模块依赖是否形成循环；
- API 是否具有稳定契约；
- 输入校验是否完整；
- 权限是否可能被绕过；
- 测试是否覆盖边界；
- 数据库迁移是否可回滚；
- 代码是否符合长期维护要求。

这些属于 AI 工程团队和确定性质量系统的职责。

### 2.2 “AI 知道知识”不等于“AI 能稳定交付”

AI 具备大量软件工程知识，但知识本身不产生以下能力：

- 持续遵守项目规范；
- 在跨会话中保持同一架构；
- 识别自己的盲点；
- 抵抗范围扩大和需求漂移；
- 证明代码实际被正确验证；
- 在发现问题时主动阻止交付；
- 在多个角色之间保持责任分离。

Loop 工程的作用，是把知识外化成角色、契约、流程、工具、状态、证据和停止条件。

### 2.3 真正的成功标准

系统成功不等于产生了很多文档，也不等于每轮 reviewer 都返回 `PASS`。

真正的成功标准是：

1. 用户只需要描述目标、关键取舍和产品体验。
2. Codex 能完成需求澄清、设计、拆任务、实施、验证、评审、修复、交付和交接。
3. 每一项 AI 生成的软件产出都有可复核的需求、设计、代码、测试和质量证据。
4. 没有确定性质量证据的结果不能被称为技术交付完成。
5. 角色之间存在真实的职责边界，生成者不能独自批准自己的结果。
6. 需求、架构、接口和代码可以跨会话连续恢复。
7. 失败、阻塞、过期结果和风险会被明确暴露，而不是被措辞包装成完成。
8. 最终产品可以构建、测试、运行、部署、观察和恢复。

## 3. 当前基线与已识别问题

### 3.1 当前已有能力

当前仓库已经包含一部分治理和 Loop 实验资产：

- `.ai/` 项目状态、任务、Gate、证据和交接记录；
- `stable/` 中的 Loop 协议候选入口；
- `roles/` 中的 writer、reviewer-plan、reviewer、repair、handoff editor 角色简报；
- `templates/` 中的 task card、run summary、review report、repair task 模板；
- `runs/` 中 writer -> reviewer-plan -> reviewer -> repair -> reviewer 的过程示例；
- 候选 Project Governor 脚本和治理一致性测试；
- 候选 `validation_runner.py` 和结构化 unittest 结果适配器；
- 状态、证据、Gate 和 HANDOFF 的边界设计。

这些内容证明项目已经认真处理了治理、权限、状态连续性和证据可信度问题。

### 3.2 当前存在的层次缺口

当前 Loop 资产主要验证：

```text
任务和治理文件是否正确
-> reviewer 是否评审
-> repair 是否完成
-> 状态和 HANDOFF 是否连续
```

尚未形成完整的产品工程质量层：

```text
代码行为是否正确
-> 测试是否覆盖行为和失败路径
-> lint/type check 是否通过
-> 构建是否成功
-> coverage 是否达标
-> 架构依赖是否合理
-> 安全检查是否通过
-> 用户路径是否可用
-> 部署和回滚是否可行
```

当前仓库存在候选代码测试和受控验证脚本，因此不能简单表述为“完全没有任何 test runner”。更准确的表述是：

> 当前有治理候选代码的局部确定性测试，但没有一个与真实产品交付绑定的、项目级的、强制性的质量基线，包括统一测试入口、lint、类型检查、构建、coverage、安全和发布验证。

### 3.3 过程评审不能替代产品质量评审

文档 reviewer 可以检查：

- 设计是否覆盖要求；
- 状态和边界是否清晰；
- 证据是否完整；
- 语义是否漂移。

但这不能证明：

- 一行产品代码行为正确；
- 所有异常路径已经处理；
- 用户真实流程可用；
- 架构可以承受后续功能；
- 安全和部署没有风险。

因此，治理评审、代码评审、架构评审、质量评审和用户验收必须分别建模。

### 3.4 语义分类和状态来源必须分离

Loop 工程的连续性不能只保存一个“当前任务标题”。每次会话和每份 HANDOFF 都必须分开保存以下五类语义：

#### 出发点与最终目标

来源：`.ai/PROJECT.md` 的权威项目目标。

内容：帮助无代码能力、无项目管理背景的用户，借助 Codex 和 Loop 工程方式，从粗略需求推进到真实可用、可部署、可验收、可持续迭代的软件产品交付。

这不是当前任务标题，也不能被某个实验仓库的拟议产品身份替代。

#### 基本立场与职责

来源：项目职责和明确授权边界。

内容：用户负责目标、关键取舍和 Gate 批准；Codex 负责澄清、设计、拆任务、实现、评审、修订、验证、交付和交接，并只能在明确授权范围内行动。

#### 手段边界

Loop、治理、Gate、评审、证据、HANDOFF 和控制器都是实现真实软件交付的手段，不能成为项目本身，也不能替代真实软件交付。

#### 当前讨论主题

必须来自显式的当前方向来源，不能从已完成任务的历史标题自动推断。

在不同时间，当前讨论主题可以是治理修复、产品定义、架构设计或具体实现；它必须明确记录，不能由 `current_task_id` 单独推导。

#### 当前问题与状态

必须根据当前 `state.yaml`、Gate、task graph、证据和交接事实合并判断，至少区分：

- 当前任务是否完成；
- 是否存在 blocking finding；
- 是否存在 pending Gate；
- Gate 是待审批、已批准未执行还是已执行；
- 是否发生用户验收；
- 是否获得 installation、activation 或 real-project entry 授权。

`proposed_product_identity` 只能标记为提案，不能写入项目最终目标、当前事实或已授权范围。历史任务完成也不能自动成为当前讨论主题。

## 4. 设计原则

### 4.1 用户目标是上位约束

用户拥有：

- 目标；
- 业务事实；
- 关键取舍；
- 风险接受；
- Gate 批准；
- 产品结果验收。

AI 不得把自己的工程建议写成用户业务决定。

### 4.2 角色有固定立场，不是临时换面具

每个角色必须长期、稳定地保护某一类价值：

- 产品经理保护目标和用户价值；
- 项目经理保护范围、依赖和进度；
- 架构师保护系统一致性和演进性；
- 开发工程师保护实现质量和可维护性；
- 质量工程师保护交付质量和失败暴露；
- 安全工程师保护安全边界；
- 交付经理保护上线和运行结果。

角色不能因为当前执行方便而放弃自己的核心立场。

### 4.3 角色扮演必须有工程约束

“深度角色扮演”不能只靠人格描述。每个角色必须有：

- 身份和经验背景；
- 固定立场；
- 任务使命；
- 输入资料；
- 必须输出的工程产物；
- 检查清单；
- 可否决的事项；
- 禁止越权的事项；
- 证据格式；
- 交接协议；
- 失败和阻塞条件。

### 4.4 生成者不能独自批准自己

代码生成 AI 不能单独宣布代码合格。架构师不能单独宣布架构可交付。测试执行者不能单独宣布产品验收。任何 `PASS` 都必须说明：

- 谁产生；
- 检查了什么；
- 使用了什么输入；
- 证据在哪里；
- 没有检查什么；
- 结论只对什么范围有效。

### 4.5 确定性检查优先于语言模型判断

能用机器重复检查的内容必须机器检查：

- 测试；
- lint；
- 类型检查；
- 构建；
- coverage；
- 依赖漏洞；
- 格式；
- 架构依赖；
- API schema；
- migration 安全性；
- 许可证；
- 配置和秘密泄漏。

AI 负责理解、设计、权衡、发现复杂问题和解释证据，不负责替代所有确定性检查。

### 4.6 失败必须阻断，而不是被语言弱化

以下情况必须进入明确的阻塞状态：

- 没有需求基线；
- 没有架构约束；
- 没有测试入口；
- 没有可执行验收标准；
- 关键验证未运行；
- 评审和实现由同一上下文自证；
- 需求发生未处理变化；
- 代码修改超出任务范围；
- 安全风险未处理；
- 构建或部署不可复现。

不能用“基本完成”“理论上可行”“后续再补测试”替代阻塞结论。

### 4.7 任务采用垂直切片

不先把所有文档、所有数据库、所有 API 或所有 UI 做完再连接，而是每次完成一条可运行、可测试、可验收的完整路径。

### 4.8 每个角色和每个阶段都必须是一个 Loop

Loop 不是“一个主控角色把工作分给若干子角色”。那仍然会把所有质量寄托在主控是否正确选择角色、角色是否认真执行以及最后是否愿意返回 PASS。

正确的单位是：

```text
角色 Loop：角色在自己的职责内完成计划、执行、验证、评审、修复和交付
阶段 Loop：一个阶段内的角色团队完成协作，并形成供人审阅的阶段交付包
项目 Loop：人批准阶段结果后，项目进入下一阶段并重复上述过程
```

一个阶段即使只有一个 Agent，也不能跳过角色 Loop。一个阶段如果由多个角色组成，每个角色先完成自己的角色 Loop，阶段团队再完成集成 Loop。

### 4.9 人是阶段放行者，不是代码检查员

人不需要逐行审查代码，但必须阅读人类可读的阶段交付包，确认：

- 阶段目标是否完成；
- 关键方案和取舍是否符合意图；
- 已知风险是否可以接受；
- 是否允许进入下一阶段。

没有人的阶段放行，系统不能自动把一个阶段的产物升级为下一阶段的正式输入。

## 5. 总体架构

### 5.1 八层结构

```text
L1 用户意图与产品目标层
L2 需求、范围与验收层
L3 项目治理与主控编排层
L4 专业角色与职责层
L5 架构、接口与实现设计层
L6 确定性质量与安全验证层
L7 交付、运行、监控与恢复层
L8 证据、版本、连续性与学习层
```

这八层是能力层，不是 Agent 的上下级组织图。主控、角色和人类 Gate 是协作关系；任何角色都必须在自己的 Loop 内完成职责，不能因为存在主控就跳过本角色的专业验证。

### 5.2 层职责

#### L1 用户意图与产品目标层

输入：用户的目标、痛点、业务事实和关键取舍。

输出：用户可理解的产品目标、用户结果和优先级。

禁止：AI 自行替用户做业务目标选择。

#### L2 需求、范围与验收层

输入：用户意图。

输出：需求基线、requirement IDs、非目标、验收标准、约束、风险和成本界限。

禁止：把聊天中的模糊表达直接当成 committed requirement。

#### L3 项目治理与主控编排层

输入：需求、任务图、角色输出、证据和用户 Gate。

输出：阶段、任务、顺序、授权、状态、下一步提示词和交接。

禁止：替用户批准 Gate，或把任意角色 PASS 直接提升为用户接受。

主控在这里是状态、顺序、权限和阶段边界的协调层，不是替代项目经理、架构师、开发工程师或质量工程师的超级角色。

#### L4 专业角色与职责层

输入：明确的任务包和相关上下文。

输出：角色专属设计、实现、评审和质量产物。

禁止：跨职责越权，或在没有输入和证据时凭身份宣称结论。

#### L5 架构、接口与实现设计层

输入：需求基线和质量约束。

输出：整体架构、模块设计、接口契约、数据模型、函数设计、依赖关系和编码规范。

禁止：先写代码再倒推架构，或通过代码绕过未解决的架构冲突。

#### L6 确定性质量与安全验证层

输入：代码、测试、配置、架构和质量 profile。

输出：可重复的测试、lint、类型、构建、coverage、安全和架构检查结果。

禁止：把 stdout 中的一句 PASS 作为全部质量证据。

#### L7 交付、运行、监控与恢复层

输入：经过验证的构建产物和运行配置。

输出：部署方案、运行检查、监控、日志、告警、回滚和恢复证据。

禁止：把本地测试通过直接等同于上线可用。

#### L8 证据、版本、连续性与学习层

输入：所有阶段产物和结果。

输出：变更记录、证据 manifest、版本关系、HANDOFF、风险历史和改进建议。

禁止：用交接文档替代真实系统状态，或用历史任务标题推断当前主题。

## 6. AI 软件工程团队角色体系

### 6.1 角色合同的统一结构

每个角色都必须使用以下合同结构：

```yaml
role_id:
role_name:
mission:
fixed_stance:
responsibilities:
non_responsibilities:
must_read:
inputs:
required_outputs:
quality_checks:
veto_rights:
forbidden_actions:
evidence_requirements:
handoff_contract:
stop_conditions:
```

### 6.2 用户与 Owner

#### 固定立场

保护真实目标、业务事实、关键取舍、风险接受和最终产品体验。

#### 负责

- 说明希望解决的问题；
- 确认业务规则；
- 选择关键取舍；
- 批准适用 Gate；
- 确认产品是否解决了真实问题。

#### 不负责

- 逐行审查代码；
- 设计模块和函数；
- 判断测试覆盖率是否合理；
- 批准 AI 自己的技术结论。

### 6.3 产品经理 Agent

#### 固定立场

保护用户价值、需求清晰度、范围边界和可验收性。

#### 负责

- 需求访谈和澄清；
- 用户故事和使用场景；
- 需求优先级；
- MVP 和非目标；
- 业务规则；
- 验收标准；
- 需求变更影响说明。

#### 必须交付

- Product Brief；
- Requirement Baseline；
- User Journey；
- Acceptance Criteria；
- Non-goals；
- Open Questions；
- 需求覆盖矩阵。

#### 可否决

- 需求无法验收；
- 技术方案遗漏核心用户场景；
- 任务实现了错误目标；

- 依赖关系；
- 当前阶段；
- 任务排布；
- 阻塞管理；
- 变更登记；
- 进度和风险报告；
- 跨会话恢复。

#### 必须交付

- Task Graph；
- Task Cards；
- Dependency Map；
- Milestone Plan；
- Risk Register；
- Blocker Register；
- Next Action。

#### 可否决

- 任务过大无法在一个会话完成；
- 依赖未满足；
- 任务目标和当前需求不一致；
- 并行写入会造成状态冲突。

#### 不得做

- 自行改变产品目标；
- 用新增下游任务逃避当前返工；
- 把任务状态写成没有证据支持的完成。

### 6.5 交付经理 Agent

#### 固定立场

保护交付物完整性、上线准备度、可部署性、可运行性、回滚和交接质量。

- 交付包和交接包。

#### 可否决

- 没有构建或部署证据；
- 没有回滚方案；
- 运行配置不完整；
- 交接无法恢复；
- 已知 blocker 被隐藏。

### 6.6 系统架构师 Agent

#### 固定立场

保护整体架构的一致性、边界、演进性、可测试性和风险控制。

#### 负责

- 整体系统架构；
- 技术栈和依赖原则；
- 服务或应用边界；
- 数据流和控制流；
- 关键质量属性；
- 安全和权限边界；
- 可观测性；
- 部署拓扑；
- 版本演进和扩展策略。

#### 必须交付

- Architecture Overview；
- Context Diagram；
- Container/Module Diagram；
- Data Flow；
- Quality Attribute Scenarios；
- Technology Decisions；
- ADR；
- Architecture Constraints；
- Architecture Verification Plan。

#### 可否决

- 组件职责重叠；
- 循环依赖；
- 关键数据流不可追踪；
- 安全边界模糊；
- 方案无法测试、部署或恢复；
- 实现方案绕过架构决策。

#### 不得做

- 只画漂亮图而不定义接口和约束；
- 用未来重构承诺掩盖当前不可维护设计；
- 未经用户批准替换重大技术取舍。

### 6.7 模块架构师 / 组件设计师 Agent

#### 固定立场

保护局部结构的清晰、可组合、可替换和可测试。

#### 负责

- 模块清单；
- 组件职责；
- 接口和输入输出；
- 数据模型；
- 类、函数和方法设计；
- 依赖方向；
- 错误模型；
- 边界条件；
- 测试边界；
- 组件组合和装配关系。

#### “乐高式”交付要求

设计必须回答：

- 成品由哪些组件组成；
- 每个组件解决什么问题；
- 每个组件包含哪些最小单元；
- 最小单元的输入、输出和不变量是什么；
- 组件之间通过什么接口连接；
- 哪些组件可以替换；
- 哪些依赖是允许的；
- 哪些依赖必须禁止；
- 如何独立测试每个组件；
- 组件组合后如何验证整体行为。

### 6.8 技术负责人 Agent

#### 固定立场

#### 可否决

- 临时方案没有退出条件；
- 技术债没有记录和风险说明。

### 6.9 开发工程师 Agent

#### 固定立场

保护实现正确性、可读性、可维护性、测试性和编码规范。

#### 负责

- 依据需求、架构和任务卡实现；
- 遵守代码规范；

- 处理错误和边界；

#### 不得做

- 自行替换整体架构；

### 6.10 质量工程师 Agent

#### 固定立场

保护质量事实，宁可阻塞交付，也不允许无证据完成。

#### 负责

- 测试策略；
- 测试层级；
- 测试数据和 fixture；
- 验收映射；
- 缺陷分级；
- 质量门禁；
- coverage 标准；
- 回归范围；
- 评审方案；
- 复验和交付质量判断。

#### 必须交付

- Quality Plan；
- Test Plan；
- Requirement-to-Test Matrix；
- Test Results；
- Defect Report；
- Coverage Report；
- Quality Verdict；
- Residual Risk。

#### 可否决

- 关键需求没有测试；
- 测试只覆盖 happy path；
- 测试结果不可复现；
- coverage 或质量门禁缺失；
- 修复没有回归验证；
- 交付物无法验证。

#### 不得做

- 只看 AI 输出是否好看；
- 用测试数量替代测试质量；
- 为了进度自行降低质量标准；
- 对自己的修复同时做唯一评审。

- 资源和成本风险；
- 性能回归。

### 6.13 独立代码评审员 Agent

- 不直接修改被评审代码；
- 不由生成代码的同一阶段自我批准。

#### 必须输出

- correctness findings；
- architecture findings；
- security findings；
- maintainability findings；
- test adequacy findings；
- severity；
- exact location；
- required change；
- verdict。

#### 固定立场

#### 负责

- 构建物；
- 环境配置；
- 部署步骤；
- 健康检查；
- 日志和监控；
- 告警；
- 回滚；
- 灰度或分阶段发布；
- 运行中故障恢复。

### 6.15 角色能力不能靠提示词宣称

“你是一名有十年经验的架构师”只能提供行为方向，不能证明这个角色真的具备生产级能力。角色能力必须由可观察的输入、工具、过程、产物和结果共同证明。

每个角色都必须有 `Role Capability Profile`：

```yaml
role_id:
role_version:
supported_stacks:
supported_task_types:
required_knowledge:
required_tools:
required_artifacts:
required_checks:
competency_challenges:
minimum_pass_conditions:
known_failure_modes:
abstention_conditions:
independent_verification:
capability_expiry_policy:
```

角色在没有能力 profile、没有对应工具、没有对应技术栈经验或没有通过能力挑战时，只能返回 `CAPABILITY_UNAVAILABLE` 或 `USER_DECISION_REQUIRED`，不能靠语气冒充专家。

### 6.16 角色实际生效的六层机制

每个角色必须经过以下六层，才允许承担生产任务：

1. **角色合同**：明确固定立场、职责、禁区、输入、输出和否决权。
2. **上下文绑定**：读取正确版本的需求、架构、规范、代码、测试和历史风险。
3. **工具绑定**：使用角色所需的确定性工具、检查器、编译器、测试器或分析器。
4. **能力挑战**：在隔离 fixture 中处理已知任务和已知缺陷，证明不是只会生成漂亮答案。
5. **生产任务证据**：在实际阶段中产出可审计的设计、代码、测试、检查和决策记录。
6. **独立效果验证**：由其他角色、确定性工具或人类阶段 Gate 验证结果，不能只接受角色自评。

### 6.17 角色能力认证

角色认证不是一次永久通过，而是与技术栈、角色版本和任务类型绑定。

认证至少包含：

- 正常场景挑战；
- 边界和失败场景挑战；
- 反模式识别挑战；
- 需求变化挑战；
- 安全和权限挑战；
- 交付证据完整性挑战；
- 与其他角色协作的接口挑战。

能力认证必须保留：

- challenge input；
- expected output；
- actual output；
- deterministic checks；
- independent review；
- unresolved findings；
- certification verdict；
- expiry or revalidation condition。

角色认证通过只说明“具备进入某类任务的资格”，不等于具体生产任务自动合格。

### 6.18 角色失效必须可识别

角色出现以下情况时，必须降级或停止：

- 连续输出没有证据的 PASS；
- 反复遗漏同一类缺陷；
- 不遵守自己的禁止事项；
- 产物无法被下游角色消费；
- 反复修改同一问题但没有进展；
- 需要越权才能完成；
- 无法解释关键取舍；
- 在没有工具结果时声称检查已完成。

失效状态包括：

```text
CAPABILITY_UNAVAILABLE
CAPABILITY_DEGRADED
REVALIDATION_REQUIRED
ROLE_BLOCKED
```

失效角色不能继续被安排到同类生产任务中，直到完成重新认证或由人明确决定替代方案。

### 6.19 架构工程师如何真正生效

架构工程师不能只输出架构图和几段解释。它必须把架构变成后续可以执行和检查的约束。

#### 输入

- 已确认的需求基线；
- 非功能需求；
- 目标运行环境；
- 数据、权限和安全要求；
- 成本和扩展约束；
- 现有代码和依赖（如果是存量项目）。

#### 必须产出

- 系统边界；
- 容器和模块结构；
- 组件职责；
- 数据流和控制流；
- 接口契约；
- 数据模型；
- 错误和恢复模型；
- 安全边界；
- 可观测性要求；
- 部署和回滚结构；
- ADR；
- 架构规则清单；
- 架构验证计划。

#### 实际生效机制

1. 架构产物必须有版本和结构化字段，不能只有图片。
2. 模块边界必须能转换成依赖检查和 import/package 规则。
3. 接口必须能转换成 schema、contract test 或类型检查。
4. 数据模型必须能转换成迁移检查、约束和回滚检查。
5. 关键质量属性必须转换成性能、安全、可用性或恢复测试。
6. 架构师必须处理 seeded architecture challenges，例如循环依赖、错误边界缺失、接口版本不兼容和新增功能导致的边界穿透。
7. 详细设计和代码评审必须检查实现是否遵守架构约束。

#### 架构工程师的交付判定

只有当架构能被开发工程师消费、被质量工程师验证、被工具部分检查、被独立架构评审，并且关键风险有处理方案时，才能返回 `ARCHITECTURE_BASELINED`。

漂亮但不可检查的架构，只能返回 `DESIGN_INSUFFICIENT`。

### 6.20 开发工程师如何真正生效

开发工程师不能只依赖自己的判断写代码，必须受到需求、详细设计、代码规范、测试和工具链的共同约束。

#### 输入

- committed requirements；
- approved architecture；
- detailed component design；
- interface contracts；
- coding standards；
- quality profile；
- task-specific allowed_write；
- required tests。

#### 必须执行

1. 先理解和锁定任务契约。
2. 对新行为先写失败测试或明确的行为验证。
3. 按最小垂直切片实现。
4. 让编译器、类型系统、lint 和格式化工具尽早运行。
5. 对边界、错误、权限和外部输入添加测试。
6. 保持函数职责、依赖方向和接口契约。
7. 记录任何无法遵守设计的偏差。
8. 对 bug 使用 reproduce test -> fix -> regression test。
9. 在交付前运行完整的任务质量门禁。

#### 实际生效机制

- allowed_write 物理限制可修改路径；
- quality runner 真实执行测试、lint、类型和构建；
- 架构检查器检查依赖方向和禁止引用；
- contract checker 检查接口和数据结构；
- pre-commit/CI 阻断不合格变更；
- 代码评审读取冻结 diff 而不是开发者自述；
- 变更 manifest 防止无关文件混入；
- 回归测试防止修复破坏旧行为。

#### 开发工程师的交付判定

只有代码、行为测试、静态检查、构建、设计一致性和评审证据都齐全，才能返回 `IMPLEMENTATION_READY_FOR_VERIFICATION`。只“代码能跑”不能作为交付标准。

### 6.21 质量工程师如何真正生效

质量工程师不能只写测试计划，也不能只运行一条测试命令后读取“all passed”。它必须建立能够发现错误的质量系统。

#### 输入

- 需求和验收标准；
- 架构和接口契约；
- 详细设计；
- 风险登记；
- 安全和性能目标；
- 历史缺陷；
- 代码和测试变更。

#### 必须执行

1. 为每条关键需求建立测试映射。
2. 设计正常、边界、错误、权限、恢复和并发场景。
3. 选择合适的 unit、integration、contract、E2E、performance 和 security 测试。
4. 先建立可失败的测试或缺陷复现证据。
5. 使用真实实现验证关键边界，避免过度 mock。
6. 运行确定性测试 runner 并验证结果 envelope。
7. 检查 coverage 的质量，而不是只看百分比。
8. 使用 seeded defects、mutation testing 或等价的缺陷发现挑战评估测试是否真的能发现问题。
9. 对失败进行分级、定位、复验和回归。
10. 以质量证据而非 AI 语气给出 verdict。

#### 实际生效机制

- test runner 验证实际 argv、测试身份、执行数量、退出码和结果 hash；
- 测试文件和 adapter 有 fingerprint，防止结果绑定到错误版本；
- coverage 阈值作为门禁，例外必须有明确理由和人类决定；
- mutation 或 seeded defect 检查测试是否能抓住已知错误；
- 质量工程师不能修改自己的评审报告来消除 finding；
- 关键质量失败阻止阶段交付；
- 质量结果进入 Human Review Packet，由人决定是否接受剩余风险。

#### 质量工程师的交付判定

质量工程师只有在需求覆盖、测试有效性、确定性结果、缺陷状态、回归结果和残余风险都完整时，才能返回 `QUALITY_VERIFIED`。测试数量多或输出漂亮不构成质量通过。

### 6.22 角色有效性与生产结果的关系

角色能力认证、角色任务通过和产品最终可用是三个不同层次：

```text
角色能力认证
-> 角色具备处理某类工作的资格

角色任务通过
-> 角色在本次任务中按契约完成并有证据

产品用户验收
-> 最终产品行为满足用户目标
```

不能用其中任意一层替代另外两层。

## 7. 主控会话与新会话模型

### 7.1 主控会话

主控会话负责：

- 读取权威项目事实；
- 识别当前阶段和当前目标；
- 维护任务图；
- 选择需要的专业角色；
- 生成 Task Delivery Packet；
- 选择是否需要独立评审；
- 收集证据；
- 判断是否阻塞；
- 生成 repair prompt；
- 编排下一个任务；
- 保持用户决策边界。

主控会话不得：

- 代替用户作业务取舍；
- 批准自己的 Gate；
- 把 AI 评审 PASS 变成用户验收；
- 用历史任务标题推断当前主题；
- 在授权外创建下游任务或修改生产。

### 7.2 任务执行会话

一个任务执行会话只负责一个明确任务，必须完成：

```text
STARTUP
-> CONTRACT_LOCK
-> DISCOVER
-> PLAN
-> EXECUTE
-> VERIFY
-> SELF_REVIEW
-> REPAIR_IF_NEEDED
-> DELIVERY_EVIDENCE
-> HANDOFF
```

任务会话输入：

- task_id；
- task objective；
- user outcome；
- requirements revision；
- must_read；
- relevant files；
- allowed_write；
- forbidden effects；
- acceptance criteria；
- verification commands；
- evidence path；
- Gate and execution authority。

任务会话输出：

- 实际产物；
- changed-path manifest；
- 计划；
- 执行记录；
- 测试和验证结果；
- 自评结果；
- 未验证项；
- 阻塞项；
- HANDOFF；
- `DELIVERY_READY`、`REPAIR_REQUIRED`、`BLOCKED`、`USER_DECISION_REQUIRED` 或 `REBASE_REQUIRED`。

### 7.3 独立评审会话

以下任务必须使用独立评审会话：

- 跨模块改动；
- 公共接口；
- 安全、权限、数据、支付；
- 数据库或迁移；
- 任务状态和控制器；
- 核心业务路径；
- 高风险部署；
- 影响多个下游任务的架构变化。

独立评审会话只读，不修复，不批准 Gate，不扩大范围。

### 7.4 修复会话

修复会话只处理评审报告中的 finding：

```text
读取原任务包
-> 读取评审报告
-> 定位问题
-> 最小范围修复
-> 重新验证
-> 更新修复证据
```

修复会话不能通过新增无关功能来掩盖问题。

### 7.5 角色 Loop

角色不是一次调用，也不是拿到任务后直接输出结论。每个角色必须按自己的专业立场完成以下循环：

```text
ROLE_START
-> 读取角色上下文
-> 明确角色目标和判断标准
-> 形成角色计划
-> 执行角色工作
-> 进行角色专属验证
-> 进行反向检查和风险挑战
-> 修复角色自身发现的问题
-> 形成角色交付物
-> 标记角色状态和未解决项
```

角色 Loop 的最小交付包括：

- 角色目标；
- 角色输入；
- 角色决策；
- 角色产物；
- 角色验证；
- 发现的问题；
- 已修复的问题；
- 未解决问题；
- 对下一角色的明确约束；
- 角色是否建议进入阶段集成。

角色不能只说“我完成了”，必须回答“我依据什么完成、还没有验证什么、谁需要审阅我的结果”。

### 7.6 阶段 Loop

一个阶段是一个团队交付单元。阶段团队可以由一个或多个角色组成，但阶段必须完成自己的协作 Loop：

```text
PHASE_START
-> 阶段目标和入口条件确认
-> 角色职责和交付接口确认
-> 各角色执行自己的 Role Loop
-> 阶段集成和冲突处理
-> 阶段质量检查
-> 阶段风险和未决事项整理
-> 生成 Human Review Packet
-> 等待人类阶段 Gate
-> APPROVED_NEXT_PHASE 或 RETURN_FOR_REWORK
```

阶段 Loop 不是把所有角色的 PASS 拼在一起。阶段团队必须检查：

- 各角色产物是否互相兼容；
- 需求、架构、实现和质量结果是否同一版本；
- 角色之间的冲突是否解决；
- 阶段交付物是否足以支持下一阶段；
- 阶段是否留下会把风险推给下一阶段的未决问题。

### 7.7 阶段不能自动跳转

阶段完成后，系统必须停在人工评审点。主控可以整理事实、风险和选项，但不能替人执行阶段放行。

人的决定只有三类：

- `APPROVE_NEXT_PHASE`：允许进入下一阶段；
- `RETURN_FOR_REWORK`：要求当前阶段修订；
- `CHANGE_DIRECTION`：改变目标、范围或关键取舍，重新建立需求基线。

如果人没有决定，阶段保持 `WAITING_FOR_HUMAN_REVIEW`，不能由 Agent 自动继续。

### 7.8 阶段交付包

每个阶段结束时必须输出人能读懂的 `Human Review Packet`，至少包括：

- 阶段目标和本阶段完成范围；
- 本阶段没有完成的内容；
- 关键决策和可选方案；
- 阶段主要产物索引；
- 需求覆盖情况；
- 质量和验证摘要；
- 风险、缺陷和未决问题；
- 对成本、进度和后续工作的影响；
- 下一阶段需要什么输入；
- 明确请求人做出的决定。

人不需要阅读全部代码，但必须能通过该交付包理解阶段发生了什么、目前是否可靠、继续推进会承担什么风险。

## 8. 从需求到交付的完整生命周期

### 阶段 0：启动和上下文恢复

#### 入口条件

- 项目根目录确认；
- 规则文件存在；
- 当前任务和 Gate 可识别；
- 没有未处理的状态冲突。

#### 必须读取

- `AGENTS.md`；
- `.ai/state.yaml`；
- `.ai/HANDOFF.md`；
- 当前任务；
- `.ai/gates.yaml`；
- `.ai/task_graph.yaml`；
- `.ai/PROJECT.md`；
- `.ai/ACCEPTANCE.md`；
- `.ai/DECISIONS.md`；
- `.ai/CODEMAP.md`；
- 任务相关规范和代码。

#### 退出条件

- 生成 Session Contract；
- 明确当前目标、范围、权限和下一步；
- 通过 `validate_state.py`；
- 没有 pending Gate 或未处理阻塞。

### 阶段 1：产品发现和需求澄清

#### 目标

把用户的模糊目标变成可理解、可验收、可拆解的产品需求。

#### 必须产出

- Product Brief；
- 用户和场景；
- 核心用户旅程；
- 用户故事；
- 需求 ID；
- 优先级；
- MVP；
- 非目标；
- 业务约束；
- 成功标准；
- Open Questions；
- 风险和成本界限。

#### 禁止

- AI 自行补充关键业务事实；
- 把技术假设写成用户需求；
- 在需求未明确时直接开始实现。

### 阶段 2：需求基线和验收设计

#### 目标

把需求绑定到后续设计、任务、测试和用户验收。

#### 必须产出

- Requirement Baseline；
- Acceptance Criteria；
- Requirement-to-Artifact Matrix；
- Requirement-to-Test Matrix；
- 非功能需求；
- 安全、性能、可维护性和可部署性目标。

#### 退出条件

- 每个需求有验收方式；
- 每个重要验收有测试或可观察验证；
- 关键取舍已由用户确认或标记为 `USER_DECISION_REQUIRED`。

### 阶段 3：整体架构设计

#### 目标

设计可实现、可测试、可部署、可演进的整体系统。

#### 必须产出

- 系统边界；
- 组件和模块；
- 数据流和控制流；
- 技术栈；
- 数据存储；
- 外部依赖；
- 认证和授权；
- 配置和秘密；
- 错误处理；
- 日志、指标和追踪；
- 构建与部署拓扑；
- 回滚方式；
- 关键 ADR；
- 架构验证方案。

#### 退出条件

- 架构评审通过；
- 需求覆盖完整；
- 关键风险有缓解；
- 模块边界和接口可以进入详细设计。

### 阶段 4：组件和函数级设计

#### 目标

把整体架构细化成开发工程师可以准确实现的最小单元。

#### 必须产出

- 组件职责；
- 接口契约；
- 输入输出；
- 数据结构；
- 状态和不变量；
- 类和函数职责；
- 调用关系；
- 依赖方向；
- 错误模型；
- 测试边界；
- 代码风格示例。

#### 退出条件

- 开发工程师不需要自行猜测关键设计；
- 每个组件知道如何独立验证；
- 允许和禁止的依赖明确；
- 设计可以映射到任务。

### 阶段 5：质量方案先行

#### 目标

在写代码前定义如何证明代码质量。

#### 必须产出

- Quality Profile；
- 测试策略；
- test runner；
- test command；
- lint command；
- typecheck command；
- build command；
- coverage command；
- coverage threshold；
- security checks；
- architecture checks；
- required smoke tests；
- evidence schema；
- 缺陷等级和质量门禁。

#### 关键规则

没有 Quality Profile 的实现任务不能被标记为可交付。

### 阶段 6：任务拆解和任务包

#### 目标

把设计拆成一个会话可以完成的垂直切片。

#### 任务必须包含

- 用户结果；
- 任务目标；
- 依赖；
- 输入；
- must_read；
- allowed_write；
- forbidden；
- 验收标准；
- 验证命令；
- 预期证据；
- 停止条件；
- 需求版本；
- 架构和接口引用。

#### 任务大小

默认一个任务只完成一个完整的小能力。超过一个会话、超过一个主要独立子系统或无法在少量验收条件内表达的任务必须继续拆分。

### 阶段 7：实现

#### 开发会话必须遵守

- 先读取规范和示例；
- 先锁定需求和架构版本；
- 先写或确认测试边界；
- 小步修改；
- 只写允许路径；
- 及时运行测试；
- 不修改无关代码；
- 记录设计偏差；
- 发现需求变化时停止并分类。

### 阶段 8：确定性质量验证

#### 必须执行

- unit tests；
- integration tests；
- contract tests；
- end-to-end tests；
- lint；
- typecheck；
- build；
- coverage；
- dependency/security checks；
- architecture/dependency checks；
- migration checks；
- required smoke tests。

#### 结果必须包含

- 实际命令；
- 实际 argv；
- cwd；
- 环境摘要；
- 开始和结束时间；
- 退出码；
- 发现的测试 ID；
- 执行数量；
- 失败和错误；
- coverage 文件和阈值；
- 输入文件 fingerprint；
- 结构化结果 hash。

stdout 和 stderr 只能作为诊断证据，不能是唯一质量来源。

### 阶段 9：AI 代码、架构和安全评审

评审至少分为：

- 代码正确性；
- 测试充分性；
- 架构一致性；
- 可读性和可维护性；
- 安全；
- 性能；
- 接口和数据契约；
- 需求覆盖；
- 运行和交付风险。

评审结果必须分级：

- `PASS`；
- `REPAIR_REQUIRED`；
- `BLOCKED`；
- `USER_DECISION_REQUIRED`。

### 阶段 10：修复与回归

所有修复必须：

- 绑定原 finding；
- 明确修复路径；
- 添加或更新回归测试；
- 重新运行受影响测试；
- 重新运行整体质量门禁；
- 重新进行独立评审；
- 保留旧结果而不是覆盖历史证据。

### 阶段 11：集成和交付准备

#### 必须检查

- 所有依赖任务完成；
- 接口契约一致；
- 数据和配置完整；
- 构建产物可生成；
- 环境差异已识别；
- 日志和监控可用；
- 回滚可执行；
- 未解决风险已列出；
- 用户验收场景可执行。

### 阶段 12：用户产品验收

用户不审代码，而是根据可观察的产品场景确认：

- 功能是否解决问题；
- 结果是否符合预期；
- 关键业务规则是否正确；
- 体验和流程是否可接受；
- 是否接受明确披露的风险和限制。

技术质量由技术证据和专业角色负责，产品取舍和最终业务接受由用户负责。

### 阶段 13：发布、运行和交接

#### 必须产出

- release summary；
- build artifact manifest；
- deployment steps；
- environment contract；
- health checks；
- monitoring and alerting；
- rollback plan；
- known issues；
- user-facing change summary；
- HANDOFF；
- next task prompt。

### 8.1 建议的阶段划分和人工放行点

下面的阶段不是为了制造流程数量，而是为了让不同类型的专业判断在正确的时间发生。每个阶段内部都必须执行阶段 Loop，阶段结束后由人阅读 `Human Review Packet` 并决定是否继续。

#### 阶段 1：需求分析

参与角色：产品经理、项目经理、质量工程师，必要时加入安全和领域专家。

角色 Loop 重点：澄清用户目标、识别隐含需求、区分事实和假设、定义范围和非目标、建立需求版本。

阶段交付物：

- Product Brief；
- 用户场景和核心旅程；
- Requirement Baseline；
- MVP 和非目标；
- 需求优先级；
- 风险、成本和约束；
- 用户验收标准；
- Open Questions。

人需要确认：我们要解决的问题是否正确，范围是否接受，关键业务取舍是否明确。

放行条件：`REQUIREMENTS_BASELINED`。

#### 阶段 2：整体架构设计

参与角色：系统架构师、项目经理、质量工程师、安全工程师、交付经理。

角色 Loop 重点：设计整体系统边界、技术栈、组件、数据流、部署方式、质量属性和演进策略，并验证需求覆盖。

阶段交付物：

- Architecture Overview；
- 系统边界；
- 组件和模块图；
- 数据流和控制流；
- 技术选型与 ADR；
- 安全和权限边界；
- 可观测性方案；
- 部署和回滚方案；
- 架构风险登记；
- 架构验证计划。

人需要确认：这套架构是否值得承担其成本、复杂度和风险，是否允许进入详细设计。

放行条件：`ARCHITECTURE_BASELINED`。

#### 阶段 3：详细设计

参与角色：模块架构师、技术负责人、系统架构师、质量工程师、安全工程师。

角色 Loop 重点：像设计乐高一样，把系统拆到组件、接口、数据结构、类、函数、状态、不变量和测试边界。

阶段交付物：

- 组件设计；
- 接口契约；
- 输入输出模型；
- 数据结构；
- 函数和方法职责；
- 调用关系；
- 允许和禁止的依赖；
- 错误和异常模型；
- 权限检查位置；
- 测试边界；
- 详细设计评审报告。

人需要确认：开发工程师是否可以依据这些设计实现，而不需要自行猜测关键结构。

放行条件：`DETAILED_DESIGN_READY`。

#### 阶段 4：测试与质量设计

参与角色：质量工程师、测试工程师、系统架构师、开发工程师、安全工程师、性能工程师。

角色 Loop 重点：先定义如何证明软件质量，再允许代码实现开始。质量工程师必须主动寻找“如何证明失败”的方式，而不是只设计成功路径。

阶段交付物：

- Quality Profile；
- Test Strategy；
- Test Plan；
- Requirement-to-Test Matrix；
- 单元、集成、契约、功能、E2E、回归测试计划；
- lint、typecheck、build、coverage 命令；
- 安全和依赖检查；
- 架构检查；
- 性能基线和预算；
- 缺陷分级和质量门禁；
- 测试证据格式。

人需要确认：质量标准是否足以支撑上线目标，成本是否可以接受，哪些质量风险不能妥协。

放行条件：`QUALITY_BASELINED`。

#### 阶段 5：编码实现

参与角色：开发工程师、技术负责人、模块架构师，质量工程师和安全工程师提供约束检查。

角色 Loop 重点：严格基于已批准需求、架构、详细设计和编码规范实现，不在编码阶段悄悄重定义系统。

阶段交付物：

- 实现代码；
- 代码注释和接口文档；
- 实现偏差记录；
- changed-path manifest；
- 单元测试初稿；
- 本地验证结果；
- 技术债和已知限制。

人需要确认：通常不逐行看代码，而是阅读阶段摘要、重大偏差、风险和可见结果，确认是否继续进入单元测试和质量验证。

放行条件：`IMPLEMENTATION_READY_FOR_VERIFICATION`。

#### 阶段 6：单元测试和组件验证

参与角色：开发工程师、测试工程师、质量工程师、模块架构师。

角色 Loop 重点：验证最小组件、函数、状态转换、错误路径、边界和契约，不让测试只证明 happy path。

阶段交付物：

- 单元测试结果；
- 组件测试结果；
- 失败和边界测试结果；
- coverage 报告；
- 测试缺口；
- 失败根因和修复记录；
- 代码质量和静态检查结果。

人需要确认：测试证据是否足以让系统进入集成，已知缺口是否可以接受或必须返工。

放行条件：`UNIT_VERIFIED`。

#### 阶段 7：集成

参与角色：开发工程师、模块架构师、测试工程师、质量工程师、系统架构师。

角色 Loop 重点：验证组件之间的接口、数据、状态、错误传播、依赖版本和配置是否真正可以组合。

阶段交付物：

- 集成构建物；
- 接口和契约测试；
- 数据流验证；
- 外部依赖适配验证；
- 配置和环境验证；
- 集成失败记录；
- 集成回归结果；
- 架构依赖检查结果。

人需要确认：各组件组合后的整体行为是否仍符合产品目标，集成风险是否可以进入功能测试。

放行条件：`INTEGRATION_READY`。

#### 阶段 8：功能和用户路径测试

参与角色：质量工程师、测试工程师、产品经理、开发工程师、安全工程师。

角色 Loop 重点：从用户和业务场景验证完整功能，不只验证接口返回或局部函数。

阶段交付物：

- 功能测试结果；
- E2E 关键路径结果；
- 用户场景覆盖矩阵；
- 失败路径和恢复路径结果；
- 权限和角色差异结果；
- 缺陷清单；
- 用户可理解的功能验证摘要。

人需要确认：软件是否真的解决了目标问题，使用体验和关键业务行为是否符合预期。

放行条件：`FUNCTIONALLY_VERIFIED`。

#### 阶段 9：修改、修复和优化

参与角色：开发工程师、质量工程师、架构师、产品经理、项目经理。

角色 Loop 重点：处理评审和测试发现，区分缺陷修复、架构修复、体验优化和范围变化，禁止把新需求混入旧任务。

阶段交付物：

- Finding-to-Fix Matrix；
- 修复代码；
- 回归测试；
- 修复前后对比；
- 架构影响分析；
- 性能影响分析；
- 未修复问题和理由；
- 是否需要重新建立需求或设计基线的判断。

人需要确认：修复是否解决了原问题，优化是否引入新的风险，未修复项是否接受。

放行条件：`REPAIR_VERIFIED` 或 `USER_DECISION_REQUIRED`。

#### 阶段 10：压力、性能和稳定性测试

参与角色：性能工程师、质量工程师、系统架构师、开发工程师、发布运维工程师。

角色 Loop 重点：先测量基线，再定位瓶颈，再修复，再测量，不能凭感觉声称“性能很好”。

阶段交付物：

- 性能基线；
- 负载模型；
- 压力和容量测试结果；
- p50/p95/p99 等关键指标；
- 资源使用；
- 瓶颈定位；
- 修复前后对比；
- 稳定性和恢复结果；
- 性能预算结论。

人需要确认：性能目标是否符合实际使用预期，成本和容量风险是否接受。

放行条件：`PERFORMANCE_VERIFIED` 或 `PERFORMANCE_RISK_ACCEPTED`。

#### 阶段 11：阶段交付和发布准备

参与角色：交付经理、项目经理、质量工程师、发布运维工程师、安全工程师、产品经理。

角色 Loop 重点：把技术产物整理成可以交付、部署、观察、回滚和说明的完整版本。

阶段交付物：

- Release Candidate；
- 构建物 manifest；
- 版本和变更说明；
- 部署步骤；
- 环境变量和配置契约；
- 健康检查；
- 监控、日志和告警；
- 回滚和恢复方案；
- Known Issues；
- 最终质量报告；
- 用户验收包。

人需要确认：是否允许交付、部署或进入下一次真实使用；这不是 AI 或 reviewer 可以替代的决定。

放行条件：`RELEASE_READY` 或 `USER_DECISION_REQUIRED`。

#### 阶段 12：维护和持续迭代

参与角色：项目经理、交付经理、质量工程师、开发工程师、架构师、发布运维工程师、产品经理。

角色 Loop 重点：处理反馈、故障、性能变化、依赖升级、技术债和下一轮需求，同时保护既有能力不回归。

阶段交付物：

- 运行数据和用户反馈；
- 缺陷和事故报告；
- 回归分析；
- 依赖和安全更新；
- 技术债清单；
- 架构演进建议；
- 下一轮需求提案；
- 版本和变更记录；
- 维护交接。

人需要确认：哪些反馈进入下一轮、哪些风险需要立即处理、哪些范围变化需要新的产品决定。

放行条件：`MAINTENANCE_CLOSED` 或进入下一轮需求分析。

### 8.2 阶段之间的输入输出关系

阶段不能只传递一句“上一阶段 PASS”。每个阶段必须把自己的阶段交付包、版本、限制、未决问题和质量证据作为下一阶段的明确输入。

例如：

```text
需求分析交付包
-> 架构设计输入
-> 详细设计输入
-> 测试设计输入
-> 编码约束
-> 单元测试约束
-> 集成验证范围
-> 功能验收场景
-> 修复和性能目标
-> 发布和维护基线
```

如果下一阶段发现上一阶段的基线不完整，必须返回上一阶段修复或请求人做重新取舍，不能由当前阶段自行覆盖缺口。

## 9. 确定性质量层设计

### 9.1 Quality Profile

每个真实项目必须定义项目级 Quality Profile：

```yaml
quality_profile_id:
language:
framework:
test_runner:
test_command:
lint_command:
typecheck_command:
build_command:
coverage_command:
coverage_threshold:
security_commands:
dependency_commands:
architecture_checks:
smoke_tests:
e2e_tests:
performance_checks:
required_artifacts:
exception_policy:
```

### 9.2 质量门禁

最低质量门禁：

```text
QUALITY_BASELINE_PRESENT
TESTS_PASS
LINT_PASS
TYPECHECK_PASS（适用时）
BUILD_PASS
COVERAGE_MEETS_THRESHOLD（适用时）
SECURITY_CHECK_PASS
ARCHITECTURE_CHECK_PASS
REVIEW_PASS
EVIDENCE_COMPLETE
```

任一关键项缺失时，结果不能是 `DELIVERY_READY`。

### 9.3 测试层级

- unit：函数和最小组件；
- component/module：组件内部协作；
- integration：模块、数据库和外部适配器；
- contract：接口和数据契约；
- end-to-end：真实用户关键路径；
- regression：历史缺陷和高风险路径；
- smoke：构建和部署后最小可用性；
- performance：关键性能和容量目标；
- security：权限、输入、数据和依赖风险。

### 9.4 测试不是数量竞赛

coverage 只是指标，不是质量本身。质量工程师必须同时检查：

- 测试是否覆盖真实行为；
- 是否覆盖失败路径；
- 是否覆盖边界；
- 是否覆盖权限差异；
- 是否覆盖外部依赖失败；
- 是否覆盖状态恢复；
- 是否存在只为提高 coverage 的无意义测试。


### 10.2 任务完成状态

```text
PROPOSED
-> READY
-> AUTHORIZED
-> IN_PROGRESS
-> VERIFYING
-> REVIEWING
-> REPAIR_REQUIRED
-> DELIVERY_READY
-> USER_ACCEPTED

```

这些状态必须严格区分：

- `DELIVERY_READY`：技术交付证据完整；
- `USER_ACCEPTED`：用户明确确认产品结果；
- `CLOSED`：任务关闭事务完成；
- reviewer PASS、测试 PASS、validator PASS 都不是用户接受。

### 10.3 任务最终交付包

每个任务至少交付：

1. 代码、文档、配置或设计产物；
2. changed-path manifest；
3. 实际命令和退出码；
4. 测试、lint、类型、构建和安全结果；
5. coverage 结果和阈值；
6. 代码或架构评审；
7. finding 和修复记录；
8. 用户结果说明；
9. 未验证项；
10. 风险和阻塞；
11. HANDOFF；
12. 下一步安全动作。

## 11. 评审体系

### 11.1 评审类型

必须区分：

- 需求评审：做对了吗；
- 产品评审：用户价值对吗；
- 架构评审：整体结构能长期工作吗；
- 模块设计评审：组件和函数边界合理吗；
- 代码评审：实现质量可靠吗；
- 测试评审：测试能发现真实问题吗；
- 安全评审：攻击和滥用路径被处理了吗；
- 性能评审：目标和资源风险可接受吗；
- 发布评审：能上线、观察和恢复吗；
- 交接评审：下一个会话能正确恢复吗。

不能用一次“process review”代替所有评审。

### 11.2 评审独立性

独立性至少包括：

- 不使用实现者的完整推理作为评审事实；
- 使用冻结的代码和证据；
- 使用单独任务卡；
- 只读被评审对象；
- 评审者不能直接修复自己的 finding；
- 评审结论不能改变用户 Gate；
- 评审失败后由新的修复阶段处理。

### 11.3 评审报告

```yaml
review_id:
task_id:
review_scope:
review_inputs:

findings:
  - finding_id:
    severity:
    category:
    location:
    issue:
    impact:
    required_change:
    verification:
quality_evidence:
architecture_evidence:
security_evidence:
test_evidence:
verdict:
unverified:
next_action:
```

## 12. 证据与状态

### 12.1 证据分类

- requirement evidence；
- design evidence；
- architecture evidence；
- implementation evidence；
- test evidence；
- review evidence；
- repair evidence；
- release evidence；
- handoff evidence；
- user decision evidence。

### 12.2 证据必须回答

- 谁产生；
- 针对什么任务；
- 针对哪个需求版本；
- 使用了什么输入；
- 执行了什么命令；
- 结果是什么；
- 结论适用范围；
- 哪些内容没有验证；
- 是否存在未消费的需求变化；
- 是否有用户决定。

### 12.3 结果新鲜度

结果不能只看“测试是否曾经通过”，还要检查：

- 需求版本；
- 架构版本；
- 输入文件 fingerprint；
- 代码变更；
- 测试版本；
- 配置和环境；
- 未消费需求变化；
- 是否经历 rebase；
- 是否为旧 generation 结果。

旧结果只能作为旧版本证据，不能被重新包装成当前版本 PASS。

## 13. Gate、权限和角色边界

### 13.1 用户控制的事项

必须由用户明确决定：

- 产品目标；
- 重要业务规则；
- 关键取舍；
- 风险接受；
- 范围变化；
- 重大依赖；
- 数据库、权限、秘密、支付和生产数据；
- 安装、激活、部署和发布；
- 用户验收。

### 13.2 AI 可以自主处理的事项

在已批准任务内，AI 可以负责：

- 需求澄清建议；
- 技术方案；
- 任务拆分；
- 代码实现；
- 测试和验证；
- 评审和修复建议；
- 证据整理；
- 交接。

### 13.3 Gate 不是流程装饰

Gate 必须包含：

- exact scope；
- exact paths；
- allowed effects；
- forbidden effects；
- approval phrase；
- execution phrase；
- validation plan；
- rollback/recovery plan；
- failure stop conditions；
- evidence paths。

批准、执行、验证、用户验收必须保持分离。

## 14. 主要隐患和风险

### 14.1 同一模型自我确认

风险：同一个 AI 写代码、审代码、判定测试、宣布 PASS。

缓解：角色和会话分离；独立评审；确定性工具；禁止自我批准。

### 14.2 角色只有名字没有立场

风险：所谓架构师、质量工程师只是换了几个提示词，最后都服从主控的完成倾向。

缓解：固定使命、否决权、输出契约和阻塞权限；角色结论必须保留。

### 14.3 文档越来越多但产品没有变好

风险：流程产物增长，代码和真实用户路径没有交付。

缓解：每个阶段绑定用户结果；每两到三个任务必须有可运行 checkpoint；治理产物不能单独形成项目成功。

### 14.4 确定性质量层空缺

风险：没有 test runner、lint、build、coverage 和安全命令时，AI PASS 成为唯一质量来源。

缓解：Quality Profile 先于实现；缺失时 `QUALITY_BASELINE_MISSING`；关键检查不可用时阻塞。

### 14.5 测试被设计成“证明成功”

风险：测试只覆盖 happy path，或者为了通过而修改测试和阈值。

缓解：独立质量工程师；测试先行；失败路径、边界、权限和恢复测试；质量标准变更需要明确决定。

### 14.6 架构漂移

风险：每个任务局部合理，整体依赖逐渐失控。

缓解：架构版本和接口契约；架构评审；依赖图和架构检查；任何偏差必须登记。

### 14.7 需求漂移和旧结果复用

风险：需求变化后旧代码和旧测试仍被声明为最新 PASS。

缓解：requirements revision、delta、rebase、freshness 和 generation fencing。

### 14.8 安全问题被功能速度掩盖

风险：AI 生成了可工作的功能，但权限、输入、秘密和日志有漏洞。

缓解：安全工程师独立评审；安全命令和威胁模型进入必选质量门禁。

### 14.9 用户负担重新回到用户身上

风险：系统最后要求用户判断复杂技术问题。

缓解：把技术结论翻译为用户可理解的风险、选项和产品影响；用户只决定业务和风险接受。

### 14.10 过度治理和 perpetual loop

风险：为了追求绝对证明，项目永远停在设计、评审和修复。

缓解：定义最低可交付标准、重试预算、最大 rebase 次数、停止条件和用户升级点；每轮必须有真实产品增量。

### 14.11 角色冲突没有解决机制

风险：产品经理要求速度，架构师要求重构，质量工程师要求阻塞，项目经理要求按期交付，主控无法决定下一步。

缓解：定义冲突优先级：用户业务目标 > 安全和法律边界 > 质量不可接受风险 > 架构一致性 > 进度和成本优化；关键冲突进入 `USER_DECISION_REQUIRED`。

### 14.12 外部输入和提示词注入

风险：用户文档、仓库数据、日志、第三方内容中的指令被 AI 当成项目规则。

缓解：区分 trusted rules、project source、generated evidence 和 untrusted input；所有外部材料先作为数据分析，不能自动成为权限或规则。

### 14.13 角色能力幻觉

风险：角色提示词写得很专业，但角色没有对应工具、技术栈能力或缺陷发现能力，仍然输出权威口吻的结论。

缓解：Role Capability Profile、隔离能力挑战、角色认证、生产任务证据、独立效果验证和失效降级。

### 14.14 能力认证被“刷题”

风险：角色记住固定 challenge 的答案，但遇到新架构、新缺陷或新技术栈仍然失效。

缓解：使用隐藏 challenge、变体输入、真实缺陷、架构变更和跨角色协作挑战；周期性重新认证；认证不直接等于生产任务通过。

## 16. 质量约束下的 Token 和总成本设计

### 16.1 成本的正确衡量方式

Token 不能只按单次调用数量衡量。真正应该衡量的是“获得一个可交付结果所需的总成本”。

```text
有效交付成本
= 需求理解成本
+ 设计成本
+ 实现成本
+ 确定性验证成本
+ 评审成本
+ 修复成本
+ 返工成本
+ 上下文恢复成本
+ 用户等待和决策成本
```

一次调用少，但产生不可上线的屎山代码，随后需要大规模重写、重新设计、重新测试，实际总成本通常高于一次完整的 Loop。

因此：

- 多用一些 token 换取清晰架构、完整测试和一次性交付，不自动视为浪费；
- 能减少返工、误解和质量逃逸的 token，属于有效投入；
- 只有没有产生新判断、新证据、新产物或新质量保障的 token 才属于浪费。

### 16.2 不牺牲质量的成本原则

以下内容不能因为节省 token 而删除：

- 需求基线；
- 关键架构设计；
- 详细接口和组件设计；
- 关键测试；
- 安全检查；
- 独立评审；
- 修复后的回归验证；
- 阶段交付包；
- 人类阶段 Gate。

可以优化的是重复读取、无关上下文、重复解释、低价值的平行观点和无结论的长对话，而不是质量证据本身。

### 16.3 Token 预算的四级结构

#### 项目级预算

用于判断整个项目的总投入、阶段数量、返工风险和预计交付成本。

#### 阶段级预算

每个阶段有预估 token、预计角色数量、预计评审轮次和允许的返工次数。

#### 角色级预算

每个角色 Loop 有自己的输入、输出和最大重复次数。角色必须在预算内完成清晰的角色交付物，而不是无限讨论。

#### 评审和修复预算

独立评审和修复要有预算，但不能把预算不足伪装成 `PASS`。预算耗尽时应停在安全边界，返回：

```text
BUDGET_EXHAUSTED
-> 保存已有证据
-> 标记未完成项
-> 输出下一步安全动作
-> 等待人类决定是否继续投入
```

### 16.4 降低 token 浪费的方式

#### 只加载与角色相关的上下文

产品经理不需要读取全部代码；开发工程师不需要读取全部历史治理证据；质量工程师需要读取需求、架构、变更、测试和质量规范。

每个角色只读取：

- 永久规则；
- 当前阶段交付包；
- 本角色必须使用的规范；
- 直接相关的代码和测试；
- 上一个阶段的限制和未决事项。

#### 使用稳定工件引用，而不是重复粘贴全文

需求、架构、接口、测试计划和阶段交付包应有版本和 hash。下一个角色读取引用和相关片段，不重复消费整份无关历史。

#### 先使用确定性工具，再让 AI 解释

先运行测试、lint、typecheck、build、coverage 和安全扫描，再把失败摘要交给 AI 分析。不要让 AI 用大量 token 猜测一个工具可以直接回答的问题。

#### 一次规划，多次执行

阶段计划和任务图稳定后，角色会话只处理自己的任务，不在每个会话重复重新规划整个项目。

#### 只对有依赖关系的角色串行

需求和架构需要串行；互不依赖的安全检查、文档检查和测试准备可以在确定共享输入后并行。

#### 评审先看高风险区域

评审优先检查公共接口、权限、数据、错误处理、并发、外部输入、关键用户路径和架构边界，不把相同的低风险格式观点重复四轮。

#### 使用分层模型和工具

机械抽取、格式校验、结果汇总和简单一致性检查优先交给确定性脚本或低成本模型；架构、复杂推理、安全和独立评审使用更强的角色上下文。模型层级不能改变质量门禁。

#### 失败早发现

在实现前发现需求和架构问题，成本通常低于编码后返工。阶段 Gate 的意义之一，就是用较低的 token 成本阻止错误进入后续昂贵阶段。

### 16.5 成本与质量指标

系统应记录：

- 每阶段预计和实际 token；
- 每角色预计和实际 token；
- 评审次数；
- 修复次数；
- 返工原因；
- 首次交付通过率；
- `DELIVERY_READY` 的总成本；
- 用户 Gate 等待时间；
- 进入后续阶段后才发现的缺陷；
- 因上下文缺失导致的重复工作。

核心指标不是“每个会话少用多少 token”，而是：

```text
Cost per Delivery-Ready Outcome
Cost per User-Accepted Outcome
Rework Ratio
Escaped Defect Ratio
First-Pass Quality Rate
```

### 16.6 防止成本优化反而降低质量

成本优化必须通过以下方式进行：

- 减少无关上下文；
- 复用稳定工件；
- 先工具验证后 AI 解释；
- 合并同类低风险检查；
- 并行独立工作；
- 早期发现架构和需求错误；
- 限制无进展重试；
- 记录并分析返工原因。

不能通过以下方式进行：

- 删除架构设计；
- 删除测试；
- 降低 coverage；
- 取消独立评审；
- 把多个角色合成一个没有否决权的泛化 Agent；
- 让阶段自动跳过人工 Gate；
- 隐藏未完成项；
- 用“demo 可运行”替代“交付可上线”。

### 16.7 Token 成本的阶段分配原则

应把更多预算投入返工代价高的前置判断：

```text
需求和架构错误：后期返工成本最高
详细设计错误：实现和测试返工成本高
编码错误：可通过测试和评审较早发现
发布错误：运行和用户损失最高
```

因此，合理的 Loop 可能在需求、架构和详细设计阶段消耗较多 token，但这是为了减少后续大规模重写和质量逃逸。

### 16.8 人类时间也属于成本

人类阶段评审不是免费资源。阶段交付包必须：

- 先给结论和请求决定；
- 清楚展示风险和选项；
- 链接详细证据而不是强迫人阅读所有原始输出；
- 明确“如果批准，下一阶段会发生什么”；
- 明确“如果拒绝或返工，会付出什么成本”。

这样才能同时减少用户负担和返工 token。

## 17. 建议路线

### Phase A：体系定义

只读完成：

- 产品目标和边界；
- 角色组织；
- 角色合同；
- 端到端生命周期；
- Quality Profile；
- 任务交付合同；
- 评审和证据合同；
- Role Capability Profile；
- 角色能力认证和失效规则；
- 风险和停止条件。

通过标准：设计不再只描述文档 reviewer，而是覆盖需求到上线的完整工程链，并且每个专业角色都有实际生效机制。

### Phase B：工程质量基线

确定：

- 第一技术栈；
- 测试入口；
- lint；
- 类型检查；
- 构建；
- coverage；
- 安全检查；
- 架构检查；
- 架构 fitness functions；
- seeded defects 或 mutation testing；
- 结构化结果。

通过标准：任何未来实现任务都有明确的客观质量门禁，且质量工程师的测试能力可以被缺陷挑战验证。

### Phase C：角色与会话执行骨架

建立：

- 角色 Loop 合同；
- 阶段 Loop 合同；
- 阶段团队协作和集成；
- 人类可读的阶段交付包；
- 人工阶段 Gate；
- 需求、架构、质量和实现角色会话；
- 独立评审和修复会话；
- 阶段成本和 token 预算。
- 角色能力挑战和认证；
- 角色失效和重新认证；

通过标准：一个角色会话知道如何完成自己的 Role Loop，一个阶段团队知道如何完成 Phase Loop，人可以读懂阶段交付包并决定是否放行；架构、开发和质量角色已经通过相应能力挑战。

### Phase D：第一条真实垂直切片

必须包含：

- 真实需求；
- 真实架构；
- 真实代码；
- 真实测试；
- lint/type/build；
- coverage 或合理替代；
- 代码和架构评审；
- 修复和回归；
- 可观察的用户结果。

通过标准：不再只是治理文件 PASS，而是有一条真正可运行、可验证、可交付的软件路径。

### Phase E：自我验证和发布准备

用已经建设的 Loop 系统推进 `loop-engine-lab` 自身的真实改进，并验证：

- 新会话能恢复；
- 任务能交付；
- 代码质量能验证；
- 评审能发现问题；
- 修复能回归；
- 发布和回滚可说明；
- 用户只需做目标和关键决策。

## 18. 全局 Definition of Done

一个产品增量只有满足全部条件，才可称为技术交付完成：

### 需求

- 需求基线存在；
- 需求 ID 明确；
- 验收标准可测试；
- 没有未消费的需求变化。

### 设计

- 整体架构有记录；
- 模块和接口有记录；
- 关键取舍有 ADR；
- 安全、性能、可维护性和部署边界明确。

### 实现

- 代码符合任务范围；
- 代码符合编码规范；
- 函数和模块职责清晰；
- 依赖方向正确；
- 错误路径和边界有处理。

### 验证

- 测试真实执行；
- lint 通过；
- typecheck 通过或有适用说明；
- build 通过；
- coverage 达标或有明确例外；
- 安全检查通过；
- 关键用户路径通过；
- 结构化证据完整。

### 评审

- 代码评审完成；
- 架构评审完成；
- 质量评审完成；
- 安全评审完成（适用时）；
- 所有阻塞 finding 已关闭。

### 交付

- 构建物可追踪；
- 部署方式明确；
- 监控和日志明确；
- 回滚和恢复明确；
- known issues 明确；
- HANDOFF 可恢复；
- 用户可以根据可观察结果进行验收。

## 19. 还需要用户决定的事项

本提案不能替用户决定以下问题：

1. 第一版系统是本地文件/CLI、Codex 工作流插件、Web 工具，还是组合形态。
2. 第一条真实产品垂直切片具体解决什么用户问题。
3. 初始技术栈和运行环境。
4. MVP 的成本、速度、质量和功能取舍。
5. 第一版是否需要真实部署，还是先完成本地可交付闭环。
6. 哪些风险可以接受，哪些风险必须零容忍。
7. 哪些角色必须独立新会话，哪些低风险任务可以在同一会话内完成。

这些决定完成前，AI 只能给出候选方案和影响分析，不能把候选方案写成项目事实。

## 21. 最终结论

Loop 工程真正要建设的不是“让 AI 多写几轮提示词”，而是让 AI 研发从一个没有责任边界、没有可验证质量、没有独立判断的生成过程，变成一个具备：

- 产品角色；
- 项目角色；
- 架构角色；
- 开发角色；
- 质量角色；
- 安全角色；
- 发布角色；
- 独立评审角色；
- 确定性工具；
- 明确契约；
- 真实证据；
- 强制阻塞；
- 可恢复交接。

这些角色不能停留在文档中的职业名称或提示词中的人格描述。每个角色都必须有能力档案、工具链、能力挑战、生产任务证据、独立效果验证和失效处理。否则“架构师”“开发工程师”“质量工程师”只是同一个模型换了名字。

生产级不是一个角色自称达到的等级，而是通过以下证据逐步建立的结果：

```text
角色能力认证
-> 角色 Loop 交付
-> 确定性质量检查
-> 独立架构/代码/质量评审
-> 阶段 Human Review Packet
-> 人类阶段 Gate
-> 真实用户路径和运行验证
```

即使角色由同一个人或同一个模型执行，也必须按不同职责分别完成 Loop、分别产出证据，并在适用时由独立上下文、确定性工具或人进行复核。

只有这样，非技术用户才不需要被迫承担代码审核职责，AI 的技术能力才可能被组织成可以持续交付的软件工程能力。

在当前阶段，最需要补齐的不是更多 process reviewer，而是：

1. 角色体系和职责边界；
2. 架构和组件级设计契约；
3. 产品级 Quality Profile；
4. 确定性测试、构建、安全和架构验证；
5. 独立代码与架构评审；
6. 从需求到发布的完整交付闭环；
7. 角色 Loop 和阶段 Loop 的真实运行；
8. token 总成本和返工成本的可观测性；
9. 一个真实的、可运行的第一条垂直切片。

这份文档应作为后续产品定义、架构设计、任务拆解和质量体系设计的候选基线，而不是最终批准的协议。
