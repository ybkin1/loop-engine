# Loop Engine 治理恢复与整体修复计划

## 目标

在不改写历史证据、不绕过 Gate、不把测试结果当用户批准的前提下，修复当前治理系统的事实源漂移，使以下链条重新闭合：

```text
state.yaml
  ↔ current task file
  ↔ task_graph.yaml
  ↔ gates.yaml
  ↔ evidence index
  ↔ HANDOFF/current projection
  ↔ continuity hashes
```

同时修复版本声明、角色契约完整性、Git 缓存污染和“任务可绕失”机制，使以后不能再出现“有提交脚本/证据目录，但没有任务、Gate、任务图和可验证完成状态”的情况。

本计划不会把现有历史任务或历史证据强行改写为当前事实；历史内容只通过新的 reconciliation/correction 证据解释和替代。

# 执行阶段

## 阶段 0：建立治理恢复任务和 Gate（只在用户批准后执行）

新增一个专门的治理修复任务，例如 `T-0046: Governance State Reconciliation and Delivery Integrity`，不把 T-0045 伪造为已存在任务。

任务卡必须明确：

- 目标：恢复 state/task/graph/gate/handoff/evidence/continuity 一致性；
- 模式：FULL；
- 阶段：S6-delivery（治理修复，不进入真实业务项目）；
- allowed paths：仅包括治理文件、校验器、版本清单、角色定义、项目忽略规则、对应测试和新证据目录；
- forbidden paths/effects：生产、部署、数据库、权限、密钥、支付、真实业务项目、历史 evidence 原文覆盖；
- 完成条件：确定性 validator 全部通过，独立一致性测试通过，工作区分类完成，且没有未经解释的当前状态漂移。

创建对应的用户 Gate，明确 `execution_status`，并保留已有 T-0040 Gate 为历史记录，不篡改其授权范围。

> 这一步是状态恢复的授权入口。未获得该 Gate 前，不写入项目文件。

## 阶段 1：构建事实源与当前投影（P0）

### 1.1 恢复任务链，但不伪造完成状态

建立当前任务、任务文件、任务图节点和 Gate 的一一对应关系：

- T-0040：依据真实证据决定是 `completed` 还是 `blocked/incomplete`；不能仅依据 commit message 或 HANDOFF 文本判定。
- T-0041：仅在真实垂直切片证据存在时标记完成；当前只有提交辅助脚本时保持 `incomplete/blocked`。
- T-0042~T-0044：保留现有任务目标，补充正式 evidence index；缺少验收证据的任务不标记 completed。
- T-0045：不恢复成“已完成”任务；如果其代码实际属于某个已有任务，则建立 superseding/correction 说明；如果仍需继续，则由新的任务卡明确承接。
- 当前 `state.current_task_id` 指向新建且已批准的治理恢复任务，而不是指向缺失的 T-0045。

### 1.2 强化确定性一致性校验

扩展现有 `.zcode/tools/validate_state.py`、`.zcode/tools/governor_lib.py` 或其现有检查层，沿用现有 Loop 约束，不另造第二套状态机。新增硬检查：

- current task 文件存在且在 task graph 中恰好一次；
- graph 中所有非历史活动任务都有任务文件；
- task file、task graph、state 的状态可解释且不冲突；
- Gate 的 `task_id` 必须存在；
- current gate 必须属于 current task，或明确为无 Gate 的终态；
- `approved` Gate 的 execution lifecycle 与 continuity auditor 一致；
- approved/in-progress 任务的 approval/execution evidence 存在；
- task graph 的 edges 与任务声明一致，不能继续使用无法解释的 `edges: []` 作为当前活动链；
- 历史旧任务允许使用 legacy 状态格式，但必须明确标记为 historical，不再把历史格式错误混入当前任务错误。

新增机器可读错误码，例如：

- `CURRENT_TASK_FILE_MISSING`
- `CURRENT_TASK_NOT_IN_GRAPH`
- `TASK_GRAPH_NODE_WITHOUT_TASK_FILE`
- `GATE_TASK_MISMATCH`
- `GATE_EXECUTION_STATUS_MISSING`
- `HANDOFF_STATE_MISMATCH`
- `CONTINUITY_SOURCE_DRIFT`

### 1.3 统一 continuity/handoff 生成

不要手工改写旧 HANDOFF 内容。使用现有 continuity producer/auditor 模式，新增当前投影 manifest，至少记录：

- state hash；
- task graph hash；
- gates hash；
- current task file hash；
- evidence manifest hash；
- release/plugin/core 版本；
- 当前 task/gate/phase；
- 生成时间和生成工具版本。

将 `HANDOFF.md` 变为当前稳定入口，明确其为生成投影；保留历史 handoff 快照。`HANDOFF-NEXT.md` 不再与 `HANDOFF.md` 并列表达不同当前事实，只作为下一步说明并引用同一 manifest。

所有修复采用 append-only correction evidence，不修改历史 `.ai/evidence/*` 原文。

# 完成判定

只有同时满足以下条件，才能报告修复完成：

- `validate_state.py` exit 0；
- `audit_handoff.py` exit 0；
- Gate register 与 continuity auditor 对同一 Gate 得出一致结论；
- 当前 task、task file、task graph、Gate、handoff、evidence 全部可追溯；
- 没有未解释的 continuity drift；
- 当前版本 manifest 与代码/文档一致；
- 角色完整性检查通过；
- tracked cache 不再污染工作树；
- 新增核心代码和测试都有 scope/manifest；
- 全量测试结果为本次真实运行结果；
- 历史证据未被覆盖；
- 仍需用户对最终修复 Gate 做明确批准，不能由 validator、reviewer 或测试代替。

## 明确不做

- 不把 T-0045 直接补成“已完成”；
- 不删除历史任务、历史 Gate、历史 evidence；
- 不用 `git add .` 代替资产审查；

- 不进入真实业务项目；
- 不部署、回滚、改数据库、改权限、处理密钥、生产数据或迁移；
