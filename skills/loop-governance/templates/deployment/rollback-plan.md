# 回滚方案模板

> **必填表单。** 缺任何必填项 = 打回重做。DevOps/系统架构师角色必须完整填写。
> 参考标准：**Microsoft Safe Deployment Practices**、**12-Factor App**（构建-发布-运行分离）。

|------|------|

| 关联版本 | [如：v2.3.0] |
| 回滚目标版本 | [如：v2.2.0] |
| 创建者 | [角色/姓名] |
| 创建日期 | YYYY-MM-DD |
| 版本 | v1.0 |

## 2. 回滚触发条件（必填）

### 2.1 自动回滚条件（如有）
| 条件 | 阈值 | 检测方式 | 是否启用 |
|------|------|---------|---------|
| 5xx 错误率 | [如：> 5%] | [监控告警] | [是/否] |
| API P95 延迟 | [如：> 2s] | [APM] | [是/否] |
| 健康检查失败率 | [如：> 50%] | [K8s readiness probe] | [是/否] |
| 数据库连接失败 | [是/否] | [健康检查] | [是/否] |

### 2.2 人工回滚决策条件
| 条件 | 说明 | 决策人 |
|------|------|--------|
| [如：P0 功能不可用] | [核心流程无法完成] | [部署负责人] |
| [如：数据不一致] | [发现数据错误] | [DBA + 负责人] |
| [如：安全漏洞] | [新版本引入高危漏洞] | [安全工程师] |
| [如：用户大规模投诉] | [5分钟 > 10个投诉] | [产品经理] |

## 3. 回滚方式（必填）

### 3.1 回滚级别选择
| 级别 | 范围 | 耗时 | 何时使用 |
|------|------|------|---------|
| 全量回滚 | 全部实例回退到上一版本 | [如：5分钟] | [严重问题/数据错误] |
| 部分回滚 | 仅回滚出问题的组件 | [如：3分钟] | [单组件故障] |
| 流量切回 | 将流量切回旧环境（蓝绿部署） | [如：30秒] | [蓝绿部署场景] |
| 配置回滚 | 仅回滚配置变更 | [如：1分钟] | [配置导致的问题] |
| 数据库回滚 | 回滚数据库变更 | [如：10分钟] | [数据迁移引发的问题] |

### 3.2 本次预设回滚方式
**首选方案**：[如：K8s 滚动回滚到上一版本]
**次选方案**：[如：流量切回蓝环境]
**最差方案**：[如：从备份恢复]

## 4. 回滚步骤（必填）

### 4.1 应用层回滚

| 步骤 | 操作 | 命令/操作 | 预计耗时 | 负责人 |
|------|------|----------|---------|--------|
| 1 | [确认回滚决策] | [通知相关方] | [1 min] | [负责人] |
| 2 | [停止新版本流量] | [如：kubectl scale deploy/app --replicas=0] | [30s] | [DevOps] |
| 3 | [切回旧版本] | [如：kubectl rollout undo deploy/app] | [2 min] | [DevOps] |
| 4 | [验证旧版本启动] | [如：kubectl rollout status deploy/app] | [2 min] | [DevOps] |
| 5 | [恢复流量] | [如：确认 endpoints 就绪] | [30s] | [DevOps] |
| 6 | [健康检查] | [curl /health → 200] | [1 min] | [DevOps] |
| 7 | [冒烟测试] | [核心流程验证] | [5 min] | [QA] |
| 8 | [监控确认] | [观察 15分钟无异常] | [15 min] | [全员] |

### 4.2 数据库回滚（如适用）

| 步骤 | 操作 | 命令 | 预计耗时 | 负责人 |
|------|------|------|---------|--------|
| 1 | [确认回滚可行性] | [检查是否有写入冲突] | [2 min] | [DBA] |
| 2 | [执行回滚脚本] | [如：flyway undo] | [3 min] | [DBA] |
| 3 | [验证数据完整性] | [行数/checksum校验] | [5 min] | [DBA] |
| 4 | [如回滚失败] | [从备份恢复] | [30 min] | [DBA] |

### 4.3 配置回滚（如适用）

| 步骤 | 操作 | 命令 | 预计耗时 | 负责人 |
|------|------|------|---------|--------|
| 1 | [恢复旧配置文件] | [如：kubectl apply -f config-v2.2.yaml] | [1 min] | [DevOps] |
| 2 | [重启受影响服务] | [如：kubectl rollout restart deploy/app] | [2 min] | [DevOps] |

## 6. 回滚风险

| 风险 | 可能性(高/中/低) | 影响 | 缓解措施 |
|------|-----------------|------|---------|
| 数据库回滚失败 | [中] | [服务不可用时间长] | [提前备份,准备恢复方案] |
| 缓存数据与旧版本不兼容 | [中] | [功能异常] | [回滚后清空缓存] |
| 回滚期间用户感知异常 | [低] | [体验下降] | [维护页面/优雅降级] |
| 回滚超时 | [低] | [超出维护窗口] | [提前演练回滚流程] |

## 9. 填写示例

> 以"K8s 环境 web 应用回滚"为例：

| 字段 | 示例值 |
|------|--------|
| 关联部署 | DEP-2026-07-22-001 (v2.3.0) |
| 回滚目标 | v2.2.0 |
| 自动回滚 | 5xx > 5% 持续3分钟 → 自动触发 |
| 人工回滚 | P0功能不可用 / 数据错误 / 安全漏洞 |
| 首选方案 | kubectl rollout undo deploy/app (5min) |
| 次选方案 | 切换到蓝环境旧版本 (30s) |
| 数据库回滚 | 仅新增列可回滚，DROP COLUMN phone |
| 回滚步骤 | 1.通知 → 2.切流量 → 3.rollout undo → 4.健康检查 → 5.冒烟测试 → 6.监控15min |
| 回滚后验证 | /health 200, 版本=v2.2.0, 登录/下单/支付全正常 |
| 风险 | 缓存不兼容→清空Redis; 数据库→仅DROP COLUMN低风险 |
| 演练 | 上季度桌面推演: 8min达标 |
