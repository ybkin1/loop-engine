# 弹性设计模板（resilience-design）

> **T-0136 D-02 落地。** system-architect 在架构评审阶段填写；稳定性
> 设计是发布检查清单的必填项。所有阈值必须"基于数据推导"（SLO 反推或
> 基线实测），不允许拍脑袋。
> 参考标准：Microsoft Well-Architected Reliability。

## Part A — RT 治理五阶梯（面试题：50ms→5s 治理顺序）

| 阶梯 | 动作 | 时限 | 可观测 |
|------|------|------|--------|
| 1 止血 | 限流/熔断最劣调用，防雪崩 | 5 分钟内恢复可用性 | 熔断器状态/错误率 |
| 2 定位 | 链路拆分（网关→服务→DB→第三方）+ 分位对比 | 30 分钟内 | p50/p95/p99 分位曲线 |
| 3 根因 | 慢 SQL / 锁等待 / GC / 依赖抖动 四类优先 | — | 慢日志/锁监控/GC 日志 |
| 4 根治 | 索引 / 缓存 / 异步 / 扩容 四选 | 按方案 | 修复后基线 |
| 5 验证 | 持续观察 24h 指标基线 | 24h | 对比修复前后 |

**何时看平均、何时看分位**：容量规划/资源预估看平均（吞吐相关）；
用户体验/线上告警看 p99/p999（长尾感知）；压测合格判定看 p99 + 拐点。

## Part B — 熔断阈值与恢复策略

**触发三要素（缺一不可）**：
1. 错误率阈值：如 ≥50% 持续 10s（窗口滑动）
2. 最小请求量：如 ≥20 req/s（防冷启动误判）
3. 窗口期：滑动窗口统计

**半开恢复**：
- 等待窗口（如 30s）→ 放行 10% 试探流量 → 成功率达阈值（如 ≥80%）
  → 全开；失败 → 重新熔断（指数退避 2x/4x/8x）

**阈值推导方法**（强制）：
- 基于 SLO/error budget 反推：error budget 消耗速率 → 允许的失败比例 →
  熔断阈值
- 或基于基线实测：历史错误率峰值 × 安全系数
- 禁止"抄网上的 50%/10s"当结论 —— 必须留推导过程

**快失败超时**：调用方超时 ≤ 下游 p99 的 50%（防排队堆积雪崩）。

## Part C — 降级恢复判定（三层）

1. **熔断器状态**：半开 → 全开（机制恢复）
2. **业务指标**：错误率 / RT 回到 SLO 基线并稳定 30 分钟（数据恢复）
3. **依赖健康**：下游恢复探针（依赖恢复）

**恢复 ≠ 回切**：先低流量回切（1% / 10%），各观察后再全量；回切失败立即
退回降级态。

## 本模板填写项

| 字段 | 内容 |
|------|------|
| 核心链路清单 | 每条链路：熔断/限流/降级三件套是否齐备 |
| 熔断阈值 | 错误率阈值 + 最小请求量 + 窗口 + 推导过程 |
| 恢复策略 | 半开窗口 + 试探比例 + 成功阈值 |
| 降级方案 | 降级后用户体验（业务无感知 / 降级感知二选一） |
| 超时配置 | 各下游调用超时 ≤ 其 p99 的 50% |
| 演练记录 | 注入故障 → 验证降级 → 恢复判定（复用防御演练 E1~E5 模式） |

## 角色指引

- **谁填**：system-architect（架构评审）
- **谁审**：release-engineer（发布前核对熔断配置 + 阈值推导文档）；
  quality-engineer（降级演练执行）
- **何时更新**：SLO 变化 / 依赖变更 / 演练发现偏差
