# 压测方案模板（load-test-plan）

> **T-0136 D-01 落地。** release-engineer 在发布前填写；压测报告是发布
> 检查清单的必填证据。所有合格判定必须可复核（数字 + 时间窗）。
> 参考标准：Microsoft Well-Architected Performance Efficiency。

## 1. 压测类型选择

| 类型 | 适用 | 工具 |
|------|------|------|
| 单接口压测 | 定位单点瓶颈 / 回归对比 | wrk / k6 |
| 链路压测 | 核心链路端到端（网关→服务→DB） | k6（多场景） |
| 全链路压测 | 大促前整体容量验证 | 生产回放 + 影子库 |

## 2. 流量模型（三形态）

| 形态 | 构造方式 | 用途 |
|------|---------|------|
| 正态 | k6 随机请求（按真实分布加权） | 模拟日常 |
| 锯齿 | 周期性爬升/回落脚本 | 验证弹性伸缩 |
| 尖峰 | 瞬时满速 + 持续 | 验证限流/队列削峰 |

**生产回放**：采样真实流量（去敏）在影子环境重放 —— 最接近真实，
但需防污染（见 §4）。

## 3. 测试数据构造

- **影子库**：独立数据库实例，结构同生产，数据脱敏
- **标记流量**：请求头携带压测标记（如 `X-Load-Test: 1`）→ 服务端
  识别后路由到影子资源，不落生产库
- **数据量**：覆盖目标场景（含 11 亿行级大表抽样、冷热数据混合）

## 4. 防污染生产（强制）

1. 压测标记必须被全链路识别（网关→应用→DB 连接串隔离）
2. 影子库/影子 Redis/影子 MQ 独立命名空间
3. 压测结束后校验：生产库无压测数据残留（对账计数）
4. 禁止在生产库执行写入型压测（只读压测需白名单）

## 5. 合格标准（四指标）

| 指标 | 合格线 | 说明 |
|------|--------|------|
| 目标 QPS 达成 | 100%（持续 10 分钟无降级） | 含活动峰值场景 |
| p99 RT | ≤ 3× 日常基线 | 与线上 p99 对比 |
| 错误率 | < 0.1% | 排除超时注入 |
| 资源水位 | CPU ≤ 70% / 内存无 OOM | 留 30% 余量 |

**容量上限判定**：继续加压至 RT 陡增拐点（错误率 >1% 或 p99 >5× 基线），
记录拐点 QPS = 容量上限。撑不到 2× 目标 QPS 需在报告中说明原因与缓解。

## 6. 压测报告（必填）

| 字段 | 内容 |
|------|------|
| 压测时间/环境 | YYYY-MM-DD HH:MM / 环境规格 |
| 目标场景 | 日常 / 活动峰值 / 尖峰 |
| 达成 QPS | 实测值 |
| p99 / p95 / 平均 | 实测值（三档齐列） |
| 错误率 | 实测值 |
| 容量拐点 | QPS 值 |
| 防污染证据 | 标记流量/影子库说明 + 生产残留对账 |
| 结论 | PASS / FAIL / 附条件 |

## 7. 检查点映射（release-checklist §4 新增）

- [CHECK-1] 压测报告存在且覆盖目标 QPS（含峰值场景）
- [CHECK-2] 防污染证据（影子库/标记流量说明）
- [CHECK-3] 容量拐点已测（或说明为何不需测）
- [CHECK-4] 结论 PASS 或附条件说明

## 8. 填写指引（角色）

- **谁填**：release-engineer（发布前）；quality-engineer（协助执行）
- **谁审**：delivery-manager（发布 GO/NOGO 依据）
- **何时更新**：架构变更 / 流量模型变化 / 新峰值场景
