# 性能诊断模板（performance-diagnosis）

> **T-0136 D-04 落地。** quality-engineer 在性能测试阶段使用；developer
> 在 SQL/代码级优化时使用。所有结论必须可复核（explain 记录/采样样本）。
> 参考标准：Microsoft Well-Architected Performance Efficiency。

## Part A — 长尾延迟定位（面试题：RT 正常但 p99 很慢）

**分位指标选择**：
| 场景 | 用哪个指标 |
|------|-----------|
| 系统容量规划 / 资源预估 | 平均（吞吐相关） |
| 用户体验 / 线上告警 | p99/p999（长尾感知） |
| 压测合格判定 | p99 + 拐点 |

**定位四步**：
1. 按分位切分请求（p50/p90/p99/p999 分组）
2. 长尾样本抓取（慢请求日志 + 采样）
3. 维度下钻：接口 → 服务 → DB/第三方 → GC/锁
4. 根因归类四类：慢 SQL / 锁等待（DB 锁、分布式锁）/ GC 停顿 / 依赖超时

**工具**：链路追踪（trace ID 贯穿）+ 慢请求采样；无 trace 时用日志
时间戳关联。

## Part B — 慢 SQL 优化（面试题：2s→20ms + 11 亿行）

**六阶梯**：
1. **看执行计划**（EXPLAIN）：type（ref/range 而非 ALL）、扫描行数、
   是否 filesort/temp table
2. **索引确认用上**（面试题追问）：EXPLAIN 的 key 字段 = 实际使用的索引；
   强制索引对比（FORCE INDEX）验证选择性；索引选择性 = COUNT(DISTINCT
   col)/COUNT(*)
3. 覆盖索引（避免回表）+ 联合索引顺序（最左前缀）
4. 分页优化：深分页 offset 大 → 游标 / 延迟关联
5. 写放大/锁竞争：批量写、避免行锁长时间持有
6. 最终手段：读写分离 / 分库分表

**11 亿行场景**（方案还成立吗）：
- 索引优化依然成立但收益递减 → 必须考虑：分区表、冷热分离（归档
  热数据）、数据生命周期策略
- 全表扫描类操作（count/大聚合）不再可行 → 计数表 / 汇总表 / 异步统计

## Part C — GC 排查（面试题：频繁 GC 怎么排查）

**四步**：
1. GC 日志开启（-Xlog:gc 或等价）
2. 观察 Full GC 频率与停顿（GC 视图）
3. 堆转储分析（大对象 / 内存泄漏）
4. 根因归类：大对象频繁创建 / 缓存无界 / 连接流未关闭 / 反射动态代理

**与长尾关联**：GC 停顿直接贡献 p99 长尾（Part A 联动）。

## 本模板填写项

| 字段 | 内容 |
|------|------|
| 性能基线 | 平均 / p50 / p95 / p99（四档齐列） |
| 长尾定位记录 | 慢请求采样 + 根因归类 |
| 慢 SQL 清单 | SQL + EXPLAIN 记录（key/type/行数）+ 优化动作 |
| 索引确认证据 | EXPLAIN key 字段记录/强制索引对比 |
| GC 排查记录 | GC 日志 + 堆转储 + 根因 |
| 结果验证 | 优化前后对比（RT/扫描行数） |

## 角色指引

- **谁填**：quality-engineer（性能测试 + p99）；developer（SQL/代码级优化）
- **谁审**：system-architect（架构级优化方案）；release-engineer（发布前
  性能门槛）
- **何时更新**：新慢 SQL / 性能退化 / 数据量级变化
