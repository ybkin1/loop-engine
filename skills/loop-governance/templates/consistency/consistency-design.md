# 一致性设计模板（consistency-design）

> **T-0136 D-05 落地。** system-architect 在架构评审时填写；每个数据流
> 必须标注一致性等级（强/最终）+ 依据。
> **范围声明**：本模板以「最终一致 + 补偿」为主轴；分布式事务
> （2PC/XA/事务消息）仅提及不展开（T-0136 D-05 裁剪决定）。
> 参考标准：Microsoft Well-Architected Reliability（数据一致性）。

## Part A — 缓存一致性（面试题：先删缓存 vs 先更新库）

| 方案 | 风险 | 适用 |
|------|------|------|
| 先删缓存再更新库 | 删缓存后、更新库前有读 → 读旧值回填 → 缓存长期脏 | 写少读多、容忍短脏 |
| 先更新库再删缓存 | 更新后删除失败 → 缓存保留旧值（业界主流） | 通用 |

**先更新库再删缓存的补偿**：延迟双删（删 → 延时 → 再删）+ 消息重试删除。

**强一致场景**（面试题：什么业务强一致）：支付/账务/库存扣减 →
直接读库或分布式锁串行化，不经过缓存。

**最终一致场景**：读多写少的展示类（商品详情/用户资料）→ 缓存 +
异步失效 + 对账兜底。

## Part B — 异步化取舍（面试题：哪些可异步/哪些必须同步）

**必须同步**：强一致写（支付扣款）、需要实时回执的读（用户感知核心）、
事务边界内。

**可异步**：非实时通知（邮件/短信/推送）、可延迟处理（报表/统计/计费
对账）、可补偿的副作用（积分/日志/审计）。

**异步化的代价应对**：
- 用户感知：立即返回"受理成功" + 进度查询接口 + 最终结果通知
- 数据一致性：消息不丢 + 幂等 + 对账补偿（见 Part C/D）

## Part C — 消息不丢失（面试题：如何保证不丢 + MQ 丢了怎么办）

**三层不丢**：
1. 生产端：confirm 机制（发送确认）+ 本地消息表（未确认重发）
2. MQ 端：持久化（刷盘策略）+ 副本（集群高可用）
3. 消费端：手动 ack（处理成功才 ack）+ 死信队列（重试 N 次后进 DLQ）

**MQ 本身丢消息**（降级方案）：本地消息表兜底 —— 业务库内记录事件状态，
MQ 仅作传输；对账任务扫描未完成事件重发。

**对账兜底**：定时任务比对「业务表状态 vs 消息消费状态」，不一致补偿。

## Part D — 幂等设计（面试题：生产端/消费端幂等）

- **生产端幂等**：消息唯一 ID（业务键派生）+ 发送前查重（本地消息表状态）
- **消费端幂等**：业务唯一键（订单号/流水号）+ 消费记录表唯一约束 +
  处理结果可重放（状态机幂等）
- **判定**：重放同一条消息 N 次，业务结果与执行 1 次一致

## 本模板填写项

| 字段 | 内容 |
|------|------|
| 数据流清单 | 每个数据流：一致性等级（强/最终）+ 依据 |
| 缓存方案 | 失效策略（更新后删缓存）+ 补偿机制（延迟双删/消息重试） |
| 异步化清单 | 可异步/必须同步划分 + 代价应对 |
| 消息链路 | confirm + 持久化 + 手动 ack + DLQ + 本地消息表兜底 |
| 幂等设计 | 生产端唯一 ID + 消费端唯一键 |
| 对账任务 | 业务表 vs 消息状态比对 + 补偿 |

## 角色指引

- **谁填**：system-architect（一致性决策）；module-architect（接口级幂等）
- **谁审**：quality-engineer（对账验证）；release-engineer（发布前检查）
- **何时更新**：新数据流 / 消息链路变更 / 对账发现缺口
