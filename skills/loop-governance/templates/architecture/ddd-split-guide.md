# DDD 与微服务拆分指南（ddd-split-guide）

> **T-0136 D-06 落地。** system-architect 在架构选型时使用 —— 先判断
> "要不要 DDD / 要不要拆微服务"，再谈怎么做。防止过度设计。

## 1. DDD 核心概念速查

| 概念 | 一句话 |
|------|--------|
| 限界上下文（Bounded Context） | 领域模型的有效边界（团队/语言/模型一致区） |
| 聚合（Aggregate） | 一致性边界的根实体（聚合内强一致，聚合间最终一致） |
| 领域事件（Domain Event） | 业务事实记录（跨上下文通信载体） |
| 防腐层（ACL） | 隔离外部系统模型的翻译层 |
| 事件风暴 | 领域建模工作坊（事件→命令→聚合→上下文） |

## 2. 何时用 DDD / 何时不用

**用 DDD**：业务规则复杂、多团队边界模糊、领域知识密集、需要领域语言
统一（保险/金融/医疗等）。

**不用 DDD**：CRUD 型应用、团队规模小、领域模型简单（避免过度设计 ——
DDD 的认知成本是真实代价）。

## 3. 微服务拆分决策表（四问）

| 拆分信号 | 判断 |
|----------|------|
| 团队规模 | 2 pizza 团队规则（>2 队共改一个库 → 拆） |
| 变更频率 | 独立发布诉求（不同发布节奏 → 拆） |
| 数据边界 | 能否独立拥有数据（不能独立拥有 → 不拆） |
| 失败隔离 | 单点故障影响面（核心链路共置风险 → 拆） |

四问答案必须留档（拆或不拆都要写理由）。

## 4. 拆分顺序

1. 先限界上下文（领域边界）→ 2. 再数据边界（库表归属）→
3. 再服务边界 → 4. 接口契约先行（contract-first）

**配套**：拆分迁移执行见 `templates/migration/data-migration-plan.md`
Part D（边界先行 + 兼容层 + 影子流量）。

## 5. 填写指引（角色）

- **谁填**：system-architect（决策 + 四问留档）
- **谁审**：module-architect（接口契约一致性）；delivery-manager（排期）
