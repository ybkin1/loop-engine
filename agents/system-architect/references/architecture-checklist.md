# 架构评审检查清单——系统架构师工作指南

## 1. 架构模式选择
- [ ] 选择模式匹配问题复杂度（CRUD 应用不需要 CQRS）
- [ ] 团队对所选模式有经验（完全陌生 = 3x 交付风险）
- [ ] 模式选择有明确理由（附参考案例或数据）

## 2. 模块划分
- [ ] 每个模块有唯一不可替代的职责
- [ ] 无职责重叠（两个模块负责同一件事 = 必须拆分或合并）
- [ ] 无不相关职责（一个模块包含两个不相关的事 = 必须拆分）
- [ ] 模块粒度均匀（50 行和 5000 行不应并列）
- [ ] 每个模块有明确的维护归属

## 3. 依赖方向
- [ ] 依赖方向符合分层规则（外层依赖内层、细节依赖抽象）
- [ ] 无循环依赖（直接或间接）
- [ ] 无跨层反向依赖（领域层 import API 层）
- [ ] 共享类型/工具包本身不依赖任何业务模块
- [ ] 各模块 import 只来自声明允许的依赖

## 4. 数据流
- [ ] 有明确的数据所有权（哪个模块是唯一真相源）
- [ ] 读写路径分开（CQRS 除外，需标注）
- [ ] 跨模块数据冗余有同步策略和一致性窗口声明
- [ ] 异步数据流有失败重试和死信处理策略

## 5. 技术选型
- [ ] 每个选型有至少一条可验证理由（不能用"大家都用""我熟悉"）
- [ ] License 与商业场景兼容
- [ ] 社区活跃（GitHub last commit < 6 个月 = 风险）
- [ ] 有备选方案（主选型不行时用哪个）
- [ ] 已知 CVE 在可接受范围

## 6. 非功能性需求
- [ ] 是否需要水平扩展、架构是否支持
- [ ] 预期 QPS/延迟估算、架构能否满足
- [ ] 数据持久化需求、存储选择是否合适
- [ ] 安全需求：认证/授权/加密是否考虑
- [ ] 合规要求（GDPR/HIPAA/SOC2）是否满足

## 7. 演进性
- [ ] v1 范围明确（"做所有事"不是 v1）
- [ ] v2 规划方向明确（无需详细设计）
- [ ] 架构变更触发条件明确
- [ ] 无架构死胡同（某决策导致未来无法扩展）

## 常见反模式（发现即 BLOCKED）

| 反模式 | 说明 | 动作 |
|---|---|---|
| 循环依赖 | A→B→A（直接或间接） | 直接 BLOCKED |
| 上帝模块 | 一个模块做所有事 | 要求拆分 |
| 贫血分层 | 每层只是透传无实际逻辑 | 合并层或补充职责 |
| 分布式单体 | 微服务架构但所有服务共享一个数据库 | 要求明确数据边界 |
| 全局状态 | 跨模块共享可变全局状态 | 要求封装或消除 |
| 未定义接口 | 模块间通过"约定"而非明确接口通信 | 要求定义接口 |
| 过早优化 | 为"可能"需求选复杂方案 | 选简单方案，预留扩展点 |
