# 角色冲突处理协议

当两个角色对交付物产生分歧时，按此协议处理。本协议是主控会话的唯一官方冲突处理流程。

## 核心原则

1. **主控不裁决。** 主控不具备做出技术判断的专业知识，也不应该具备。
   主控的角色是结构化呈现冲突，升级给用户。
2. **每个角色对自己的专业领域有否决权。** 质量工程师对覆盖率的否决权、
   安全工程师对 CVE 的否决权、交付经理对发布完整性的否决权——这些不是"意见"，
   是合同授予的否决权。
3. **不同角色的否决权冲突时，用户裁决。** 开发工程师认为"这个功能不需要测试，
   覆盖率低是合理的"——质量工程师的合同说"覆盖率不达标我拒签"。
   两者都无法说服对方，升级。

## 冲突分类

### A 类：数据冲突（事实性）

两个角色对同一事实有不同认定。例如：架构师说"这个模块不能依赖那个模块，
架构文档第 3.2 节写了"。开发工程师说"架构文档第 3.2 节没有这条限制"。

处理：主控读取双方引用的源文件，把原文粘贴出来，不做解释。用户看原文裁决。

### B 类：标准冲突（合同赋予的否决权）

一个角色基于自己的合同标准否决了另一个角色的产出。例如：质量工程师说"覆盖率
62%，门槛 80%，我拒签"。开发工程师说"这个项目是原型阶段，60% 就够了"。

处理：
1. 否决方必须引用自己的合同条款（哪一节的哪一条赋予了否决权）
2. 被否决方必须用自己的专业立场解释为什么这条标准不适用
3. 主控结构化呈现双方论点
4. 用户决定：维持标准 / 修改合同（降低门槛，需要 gate）/ 要求弥补

### C 类：范围冲突（谁负责什么）

两个角色对"谁该做这件事"有分歧。例如：模块架构师说"接口的错误类型定义应该
由开发工程师在做实现时补充"。开发工程师说"接口契约里没写错误类型，是架构师
的遗漏"。

处理：
1. 主控读取双方的角色合同，找出"职责范围"和"明确禁止"两节
2. 交叉对比，指出哪方合同里明确包含了这件事，或哪方合同里明确排除了这件事
3. 如果合同都无法判定，升级给用户，由用户补充合同或临时指派

### D 类：方法冲突（怎么做）

两个角色对"同一个目标的不同方法"有分歧。例如：架构师推荐微服务，
开发工程师说这个规模用单体更合适。

处理：
1. 双方都写一个简短的决策包（格式见 `templates/decision-packet.md`）：
   选项、代价、收益、为什么推荐
2. 主控把两份决策包并列呈现（不合并、不推荐）
3. 用户选择

## 升级格式

主控在升级给用户时，使用以下固定格式：

```markdown
# 角色冲突 · <冲突类型>

## 冲突方
- A: <角色A> · 产出: <文件路径>
- B: <角色B> · 产出: <文件路径>

## 分歧点
<一句话说清楚：A 认为什么，B 认为什么，为什么不能达成一致>

## A 的论据
<角色 A 的完整论点，附引用>

## B 的论据
<角色 B 的完整论点，附引用>

## 决策资料
<双方都认可的客观事实——源文件原文、工具输出、数字>

## 你的决策
- 采纳 A：<一句话后果>
- 采纳 B：<一句话后果>
- 或者：<你的第三条路>
```

## 冲突时间线

1. 下游角色发出拒收 → 附带具体原因和合同条款引用
2. 上游角色收到拒收 → 24 小时内回应（修复计划 or 反驳理由）
3. 如无法达成一致 → 主控在下一个 checkpoint 升级给用户
4. 用户裁决后 → 主控记录裁决到 gates.yaml，被驳回方按裁决执行

## 禁止的行为

- 角色绕过主控直接升级给用户（所有沟通必须经过主控——保持证据链完整）
- 角色以"用户一定会站我这边"为由提前执行
- 主控在冲突中加入自己的意见
- 角色修改对方的输出文件
