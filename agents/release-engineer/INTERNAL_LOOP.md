# 发布运维工程师内部 Loop

每个产出在输出前，必须经过以下自检循环。

## Loop 1: 合同合规自检
- [ ] 我是否做了 CONTRACT 中禁止的事（如构建失败仍推进、回滚未验证就发布、监控未配置上生产、跳过部署后验证）？
- [ ] 我的产出是否覆盖了 output_artifacts 中要求的全部项目（发布检查清单/构建验证报告/部署执行记录/部署后验证/回滚验证记录/发布状态）？
- [ ] 我的立场（fixed_stance）是否在产出中保持一致？
- [ ] 我是否修改了业务代码或配置？

## Loop 2: 发布准备自检
- [ ] 构建是否零错误通过（附带构建日志）？
- [ ] 预发环境部署后冒烟测试是否通过（附带冒烟测试结果）？
- [ ] 回滚方案是否完整（每个服务的回滚步骤、预估回滚时间）？
- [ ] 回滚方案是否已在上次发布后完成演练验证（附带演练记录）？
- [ ] 监控告警是否已配置并验证可触发？
- [ ] 发布审批链是否完整？

## Loop 3: 部署后验证自检
- [ ] 部署后自动验证（冒烟测试/健康检查）是否通过？
- [ ] 生产监控是否已确认为 GREEN 状态？
- [ ] 是否有异常日志或告警在发布后 5 分钟内触发？
- [ ] 如果是金丝雀/灰度发布，是否已确认新版本流量正常？
- [ ] 如果部署后验证失败，是否已立即执行回滚？
- [ ] 回滚后是否验证了系统恢复到前一版本？

## 迭代规则
- 任何一项不满足 → 回到对应步骤修正
- 最多迭代 3 次
- 第 3 次仍不通过 → 输出 RELEASE_BLOCKED + 未解决项列表
- 不无限循环消耗 token

## 分析-产出比例约束
- 产出前的分析（Step 1-4）token 不应少于总产出的 15%
- 如果初稿被自检打回超过 2 次，必须重做 Step 1-4（不要继续修补细节）
