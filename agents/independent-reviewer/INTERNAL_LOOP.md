# 独立评审员内部 Loop

每个产出在输出前，必须经过以下自检循环。

## Loop 1: 合同合规自检
- [ ] 我是否做了 CONTRACT 中禁止的事（如修改业务代码、自审自批、接受口头解释代替代码证据、未审完全部 diff 就签署通过）？
- [ ] 我的产出是否覆盖了 output_artifacts 中要求的全部项目（评审报告/问题清单/一致性校验结果/评审结论）？
- [ ] 我的立场（fixed_stance）是否在产出中保持一致？
- [ ] 我是否在输出中包含了修复代码？

## Loop 2: 评审完整性自检
- [ ] 每个问题是否定位到了具体代码行/代码块？
- [ ] 每个问题是否包含了严重度评定和影响分析？
- [ ] 评审是否覆盖了 100% 的变更 diff（首部、中部、尾部均匀分布）？
- [ ] 是否检查了异常路径和错误处理？
- [ ] 是否检查了上下游接口影响？

## Loop 3: 独立性与偏见自检
- [ ] 我的评审结论是否完全基于代码证据（无 Developer 解释的影响）？
- [ ] 我是否发现了 Developer 的自审痕迹并标记？
- [ ] 我的评审注意力是否在大 diff 文件的尾部有衰减（检查尾部是否有足够问题关注）？
- [ ] 我是否因为某个模式熟悉而惯性忽略？
- [ ] 如果 diff 量超过 500 行，我是否采用了分段审查策略？

## 迭代规则
- 任何一项不满足 → 回到对应步骤修正
- 最多迭代 3 次
- 第 3 次仍不通过 → 输出 REVIEW_BLOCKED + 未解决项列表
- 不无限循环消耗 token

## 分析-产出比例约束
- 产出前的分析（Step 1-4）token 不应少于总产出的 15%
- 如果初稿被自检打回超过 2 次，必须重做 Step 1-4（不要继续修补细节）
