# 代码审查清单——评审维度与判定标准

## P0 级检查点（命中=阻断交付）

### 安全
- 有无SQL注入风险（字符串拼接SQL且参数来自外部输入）
- 有无XSS风险（未转义的用户输入直接渲染到HTML）
- 有无越权风险（资源访问未校验所有权）
- 有无敏感数据暴露（日志打印密码/token）
- 有无硬编码密钥
- 有无不安全的反序列化（pickle.loads/yaml.load无SafeLoader）

### 架构违法
- 有无违反分层架构（Controller直接操作DB、Service层进入表现层）
- 有无循环依赖
- 有无绕过架构合约强制中间件（绕过auth middleware/rate limiter）

### 数据安全
- 有无明文密码存储
- 有无缺少传输加密的敏感数据端点

## P1 级检查点（记录，可能组合升级为P0）

### 可维护性
- 单函数超60行(Python/JS)或40行(Go)、嵌套深度超4层、明显重复代码块(>10行)、类承担超3个职责

### 错误处理
- 所有I/O操作有error handling、try块捕获具体异常类型、异步调用有超时、关键操作失败有回滚

### 命名与注释
- 变量名表达用途(而非x/data/tmp)、函数名准确描述行为、复杂逻辑注释"为什么"、无过期注释

## 评审报告格式（每条发现的标准结构）
```
ID: IR-XXX | 严重级别: P0/P1/P2 | 类型: security/architecture/maintainability/logic/style
标题: <一句话> | 文件: <路径> | 行号: <精确> | 代码片段: <含上下文>
影响: <用户/系统层面后果> | 合约引用: <违反的条款编号和原文>
```

## 不可接受的审查输出
- "代码整体质量良好"——没指明文件/行数/维度
- "有一些小问题但不影响"——没列出每个问题的文件+行号+代码片段
- "这个函数写得不错"——没说哪个标准维度达标
