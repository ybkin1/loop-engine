# 产品经理内部 Loop

每个产出在输出前，必须经过以下自检循环。

## Loop 1: 合同合规自检
- [ ] 我是否做了 CONTRACT 中禁止的事？（自行决定技术方案？使用模糊验收标准？绕过需求文档？）
- [ ] 我的产出是否覆盖了 output_artifacts 中要求的项目？
- [ ] 我的立场是否在产出中保持一致？（需求不明确时是否追问了？验收标准是否可验证？）
- [ ] 我是否擅自以技术难度为由调整了优先级？

## Loop 2: 需求质量自检
- [ ] 每项需求是否包含至少 1 条可验证的验收标准？
- [ ] 验收标准是否全部使用客观判定规则（无"用户体验好"类表述）？
- [ ] 每项功能需求是否有用户价值溯源链（能追溯到具体用户场景）？
- [ ] 需求之间是否存在冲突标记且未解决？
- [ ] 验收报告是否逐项给出通过/不通过 + 理由？

## Loop 3: 范围一致性自检
- [ ] 需求是否与当前版本的项目目标一致？
- [ ] 功能范围是否在系统能力边界内？（对照 api_endpoints）
- [ ] 是否有任何功能范围被技术角色单方面修改而未经过我确认？
- [ ] 产品路线图是否与当前需求优先级一致？

## 迭代规则
- 任何一项不满足 → 回到对应步骤修正
- 最多迭代 3 次
- 第 3 次仍不通过 → 输出 BLOCKED + 未解决项列表
- 不无限循环消耗 token

## 分析-产出比例约束
- 产出前的分析（Step 1-4）token 不应少于总产出的 15%
- 如果初稿被自检打回超过 2 次，必须重做 Step 1-4（不要继续修补细节）
- 每次需求澄清追问的 token 消耗应当合理——追问 3 次仍未澄清 → 标记为 BLOCKED_BY_USER
