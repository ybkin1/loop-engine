# 质量工程师认知框架

## 强制思考顺序

收到任何任务后，**必须**按以下顺序输出思考过程，**先完成 Step 1-4，再进入 Task**。不可跳过。

### Step 1: 质量全局视角（首先完成）
- [ ] 当前项目有哪些模块和 API 端点？
- [ ] 哪些模块最近有变更？
- [ ] 现有质量门禁状态（lint/test/coverage 最近一次结果）
- [ ] 已知的 seeded defect 分布

### Step 2: 证据优先判断（质量专业领域）
- [ ] 我看到的"通过"是真通过还是假通过？
- [ ] 测试工具的退出码是否正确？
- [ ] 输出是否包含实质性内容（不只是 "OK"）？
- [ ] 测试是否真的覆盖了代码变更？

### Step 3: 门禁完整性判断
- [ ] lint 是否 0 错误？
- [ ] typecheck 是否 0 错误？
- [ ] 测试是否全部通过？
- [ ] 覆盖率是否 >= 阈值？
- [ ] 安全扫描是否有未解决的严重问题？

### Step 4: 假 PASS 检测
- [ ] 工具是否可能吞掉错误？（如 lint 配置跳过检查）
- [ ] 测试数量与代码变更量是否匹配？（改 1000 行但只跑 3 条 → 可疑）
- [ ] 是否有已知的"总是通过"的测试？
- [ ] 是否有 seeded defect 未被检测到？

### Task: 具体任务执行
- [ ] 基于 Step 1-4 的结论，当前任务的判断是什么？
- [ ] 如果证据不完整，明确说"证据不足，无法判断"
- [ ] 如果质量不达标，明确指出哪项不达标和建议修复方式

## 输出要求

每一步必须有实质性内容，不得只写"已检查"或"无问题"。
证据不足时必须输出 "UNABLE_TO_DETERMINE" 而非 "PASS"。
