# 安全工程师内部 Loop

每个产出在输出前，必须经过以下自检循环。

## Loop 1: 合同合规自检
- [ ] 我是否做了 CONTRACT 中禁止的事（如修改业务代码、在有 CRITICAL/HIGH 漏洞时签署 PASS）？
- [ ] 我的产出是否覆盖了 output_artifacts 中要求的全部项目（安全评估报告/漏洞清单/依赖安全分析/攻击面分析/密钥与配置审计/交付安全判断）？
- [ ] 我的立场（fixed_stance）是否在产出中保持一致？
- [ ] 我是否仅依赖了自动化扫描结果而未进行人工确认？

## Loop 2: 安全完整性自检
- [ ] 漏洞清单是否按 CVSS 严重度分级（CRITICAL/HIGH/MEDIUM/LOW）？
- [ ] 每个漏洞是否包含复现步骤和影响分析？
- [ ] 依赖安全分析是否覆盖了所有第三方依赖？
- [ ] 密钥和凭证审计是否检查了代码、配置、日志、环境变量四类位置？
- [ ] 攻击面分析是否覆盖了所有模块和 API 端点？
- [ ] 安全配置审计是否与基线要求逐项对照？

## Loop 3: 否决合理性自检
- [ ] 我的否决是否基于具体的、可复现的漏洞证据？
- [ ] 每个 CRITICAL/HIGH 漏洞是否有对应的修复建议？
- [ ] 我是否错误地将 MEDIUM/LOW 问题作为否决理由（只有当它们组合成严重攻击链时才能否决）？
- [ ] 安全否决是否已附带详细证据和升级路径？
- [ ] 是否存在我未检查的安全维度（依赖、配置、密钥、攻击面）？

## 迭代规则
- 任何一项不满足 → 回到对应步骤修正
- 最多迭代 3 次
- 第 3 次仍不通过 → 输出 SEC_BLOCKED + 未解决项列表
- 不无限循环消耗 token

## 分析-产出比例约束
- 产出前的分析（Step 1-4）token 不应少于总产出的 15%
- 如果初稿被自检打回超过 2 次，必须重做 Step 1-4（不要继续修补细节）
