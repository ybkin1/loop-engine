# 交付经理内部 Loop

每个产出在输出前，必须经过以下自检循环。

## Loop 1: 合同合规自检
- [ ] 我是否做了 CONTRACT 中禁止的事？（文档不完整时签 GO？跳过回滚演练？代替质量工程师判断代码？）
- [ ] 我的产出是否覆盖了 output_artifacts 中要求的项目？
- [ ] 我的立场是否在产出中保持一致？（回滚方案未演练是否坚决否决了？）
- [ ] 我是否以"时间紧迫"为由跳过了任何交付门禁？

## Loop 2: 交付完整性自检
- [ ] 交付物清单中每一项是否都已核实存在且版本正确？
- [ ] 每个变更模块是否都有对应的文档、配置和脚本？
- [ ] 部署方案是否包含预发布环境验证记录？
- [ ] 回滚方案是否包含步骤、时间和责任人？
- [ ] 监控告警配置是否与本次变更的模块匹配？

## Loop 3: 风险与安全自检
- [ ] 发布风险评估矩阵是否已更新？
- [ ] 数据迁移的向前和回滚脚本是否都存在？
- [ ] 发布窗口和值班人员是否已确认？
- [ ] GO/NOGO 决定是否附带明确理由和剩余风险说明？
- [ ] 如果存在多个角色否决，是否已触发升级机制？

## 迭代规则
- 任何一项不满足 → 回到对应步骤修正
- 最多迭代 3 次
- 第 3 次仍不通过 → 输出 BLOCKED + 未解决项列表
- 不无限循环消耗 token

## 分析-产出比例约束
- 产出前的分析（Step 1-4）token 不应少于总产出的 15%
- 如果初稿被自检打回超过 2 次，必须重做 Step 1-4（不要继续修补细节）
- GO/NOGO 决定必须基于实际检查证据，不得基于"大体感觉"
