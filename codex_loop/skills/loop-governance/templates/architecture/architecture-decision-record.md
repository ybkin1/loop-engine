# 架构决策记录 (ADR)

> **必填表单。** 缺任何必填项 = 打回重做。系统架构师角色必须完整填写。
> 参考标准：**MADR (Markdown ADR)**、**arc42**（Decisions 章节）。

## 2. 背景与问题（必填）

### 2.1 上下文
[描述当前项目/系统的状态，什么触发了这个决策需求。2-3句话即可。]

**示例：**
> 系统目前使用单数据库实例，随着用户量增长（预计Q4达到100万用户），单数据库已成为性能瓶颈。高峰期查询延迟从50ms上升到500ms，需要做出架构调整。

### 2.2 待决策问题
[用一句话清晰描述需要做的决策是什么]

**示例：**
> 我们应该如何扩展数据库层以支撑未来12个月的用户增长（预计100万→500万用户）？

## 8. 填写示例

> 以一个完整的 ADR 示例：

| 字段 | 示例值 |
|------|--------|
| ADR 编号 | ADR-2026-001 |
| 标题 | 采用读写分离方案扩展数据库层 |
| 状态 | 已接受 |
| 背景 | 单数据库成为瓶颈，高峰期读延迟500ms，需扩展以支撑用户增长 |
| 驱动力 | 性能(5), 可靠性(5), 运维复杂度(4), 成本(3), 开发效率(2) |
| 方案A | 读写分离（1主2从）：成本低、团队熟悉、MySQL原生支持；缺点：复制延迟、写仍是瓶颈 |
| 方案B | 分库分表（按user_id哈希）：扩展性最强；缺点：跨分片查询复杂、开发改造成本高 |
| 方案C | 缓存层（Redis缓存热点数据）：实现简单；缺点：缓存失效问题、数据一致性问题 |
| 选定 | 方案A-读写分离 |
| 选择理由 | 成本可控（仅加从库），解决当前读瓶颈，团队有运维经验，不需要大幅度改造代码 |
| 代价 | 主从延迟(<1s)→关键业务读主库；应用改造→ORM配置即可 |
| 拒绝方案B理由 | 跨分片查询复杂，改造成本太高，当前阶段不需要 |
| 拒绝方案C理由 | 缓存一致性问题会引入新的Bug来源，仅作为补充手段 |
| 影响 | 架构(中), 代码(低), 数据库(高), 成本(中) |
| 实施 | 4周：搭建从库→配置→监控→压测→灰度上线 |
